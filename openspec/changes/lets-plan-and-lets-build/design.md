## Context

`skills/lets-build/SKILL.md` is a runner. On the default branch it finds the issue, confirms its packet, routes it, runs the glossary preflight, claims it, imports the glossary checkpoint and proposes. On a change's branch it continues the plan, applies, or finishes. Its *Propose* offers a handoff through `lets delegate handoff`. Its *Apply* has the plan reviewed with `lets-review-plan` on `lets-standard`. Its *Finish the change* invokes `lets-review-build` on the `standard` flow and finishes a `minimal` change itself.

`skills/lets-go/SKILL.md` names six of those sections by name, and repeats none. Its step table has three rows: plan runs `openspec-propose`, build runs `lets-build` and stops short of *Finish the change*, and review build runs that section. Review plan has no row: it runs inside build. `tests/skill-interfaces.bats` pins all of this as text, and the `lets-go` and `issue-comments` specs name `lets-build`'s sections. Both schemas tell the brainstorm that `lets-build` claimed the story, and tell apply to start from `lets-build` and finish through it. The routing tables send "start the next story" to `lets-build`. So do `lets-shape`'s closing handoffs and `lets-setup-backlog`'s intro.

`lets-review-build` ships in the `standard` flow only. Nothing else can finish a change on the `minimal` flow once `lets-build` stops at the last tick. #186 will give review plan a session and walk the five steps from one table; #187 will rewrite `lets-go` in plain language. This change is the fourth of the six stacked on #177. The pinned OpenSpec CLI in this repository still lists a `review` artifact, from the 0.7.0 copy of the schema. Apply depends on `tasks` alone, so the plan reaches `ready` without it.

## Goals / Non-Goals

**Goals:**
- Each step has one skill of its own name: `lets-plan` plans, `lets-build` builds, `lets-review-build` finishes, in both flows.
- `lets-go` is the only runner. The six sections live in it, and no skill names a section of `lets-build` or sends a user to `lets-build` to start work.
- Behaviour on either flow is what it was: the same claim, the same route, the same reviews, the same finish.
- The next story, #186, finds one skill per step row and one gate to move, not three places to edit.

**Non-Goals:**
- A session or report for review plan, the step table, the records check or new skip lines (#186).
- Rewriting the moved sections or the rest of `lets-go` (#187).
- Removing the `handoff` strategy, its commands, its docs or its config key.
- Changing `openspec-propose` or `openspec-apply-change`, the schemas' artifacts, or this repository's synced copies and `openspec/config.yaml`.

## Test Seams

- **Primary test seam:** `tests/skill-interfaces.bats`. It reads the skills, `flows.json`, the overlay, the schemas and the README as text. It checks fixed strings, and that every name points at something real. It also builds each flow and checks that the reference links resolve.
- **Existing seams reused:** `tests/sync-rules.bats`, which reads the rules fragment; `tests/release-build.bats` and `nix flake check`, which build both flows from `flows.json`; `tests/openspec-compat.bats`, which runs OpenSpec's CLI over each schema.

## Scrutiny Tier & Blast Radius

- **Tier:** medium
- **Blast radius:** seven skills, one new; both schemas' brainstorm and apply instructions; `flows.json`; the overlay; the README and one doc; two specs; one new decision record and one status line; two bats files. Outside the repository: every project on either flow. After `lets sync`, "start the next story" runs `lets-go`, `lets-build` builds only, and the `minimal` flow gains `lets-plan` and `lets-review-build`.

## Decisions

1. **`lets-plan` is a thin door to `openspec-propose`.** `skills/lets-plan/SKILL.md` has four parts. *Find where you are*: it runs on a change's branch, `<name>`. On the default branch it stops and says that `lets-go` starts an issue. The caller gives the issue and the route line, as `lets-go`'s plan prompt does. By hand with neither, it finds the issue with the title search `lets-go` uses, `gh issue list --state open --search "<branch> in:title" --json number,title`, and keeps the one whose title starts with `<branch> — `. *Plan*: invoke the `openspec-propose` skill for `<name>`, for #<i>, with the route line for the proposal's commit message. Say to use the schema `lets-minimal` when the route is `lets-minimal` and the flow's schema is not. Say to continue the change when it exists. With no change and no route line, stop: `lets-go` routes and claims. *When propose stops*: read `openspec instructions apply --change <name> --json`. `ready` means the plan is ready, and on `lets-standard` the review comes next. Anything else means propose stopped early. *Rules*: never plan from the default branch; no handoff, no `lets delegate` command, no build, no artifact written outside the skills it invokes. Alternative: fold the route table into `lets-plan`, so it can start a change by hand. Rejected: routing reads the Project and the parent epic, which is Start's work, and `lets-go` already carries it.
2. **`lets-build` keeps its name and one job.** The skill shrinks to *Find where you are*, *Apply* and *Rules*. *Find where you are* keeps a short table. On the default branch: say that `lets-go` starts an issue, and stop. On a branch with a change folder: read `openspec instructions apply --change <branch> --json`. `ready`: invoke the `openspec-apply-change` skill for `<branch>`; the schema's apply instruction works test-first with the `lets-test-first` skill; stop at `all_done` and say the `lets-review-build` skill finishes the change. `blocked`: say the plan is not finished, and to run `lets-plan`. `all_done` on entry: say every task is ticked, and name `lets-review-build`. Any other state: show the CLI's `instruction`, and stop. On a branch with an archive folder named `<date>-<branch>`: say the change is archived and its pull request is ready for review. On any other branch: say that `lets-plan` plans a claimed change on its branch, and that `lets-go` starts an issue. Nothing else stays: no find, confirm, route, claim, handoff, plan review or finish. Its description changes to match, so an agent that reads descriptions to pick a skill no longer picks it to start work.
3. **The six sections move into `lets-go`, with five adaptations.** They become `###` subsections of *Start*, after the numbered steps, in `lets-build`'s order: *Find the source of demand*, *Confirm the packet*, *Route*, *Glossary preflight* with *Check the prerequisite* and *Check the checkpoint* as `####`, *Claim*, *Import the glossary checkpoint* with its two `####` parts. The text moves word for word, except where a sentence stops being true in its new home. Those places are: (a) *Claim*'s branch-exists stop says to switch to the branch and run `lets-go` there. (b) *Claim*'s lost race says: when `next` picked the issue, run `next` again with the same candidates, and go on from *Start* step 3 with the new issue; the lines printed for the lost issue stand. (c) *Import the glossary checkpoint* opens: run this after *Claim* created the branch, before *Find the first unfinished step* reads the tree, and only when *Glossary preflight* found owned edits; a resumed change has its glossary edits committed, and needs no transfer. (d) *Start* step 1 inlines the default branch read, `gh repo view --json defaultBranchRef --jq .defaultBranchRef.name`, where it said to find it as `lets-build` does. (e) Every `` `lets-build`'s * `` in `lets-go` goes: the numbered steps of *Start*, *Start from an idea* step 2, *Pick the first ready story* step 1, and *Find the first unfinished step* step 4, which reads `state` on its own. The paragraph that says `lets-go` reuses `lets-build` goes too. The sentence in *Route* that the route line goes in the proposal commit stays: `lets-plan` carries it. Alternative: a shared reference file under `skills/lets-go/references/` that both skills link. Rejected: `lets-build` would not read it, and a reference is for a method, not for the steps a skill runs. Alternative: rewrite the sections as they move. Rejected: #187 owns the plain-language pass, and a near-verbatim move keeps this diff reviewable.
4. **`lets-go` with nothing takes `next`.** *Start* step 2 gains a third request form on the default branch. **Nothing** runs the third case of *Find the source of demand*, over the whole backlog, with its rank and *Check the prerequisite* per candidate. It prints `Picked #<n>: <title>, the next ready issue.` and goes on from step 3 with that issue. When nothing is ready, the case's own stop stands: the backlog has nothing ready, run `lets-shape`. The routing row sends "start the next story" to `lets-go`, so this is the one new behaviour the move needs. The level comes from the Kind as usual. Alternative: keep the stop that asks for a number or an idea. Rejected: the routing row would point at a skill that cannot start the next story.
5. **The plan review gate moves into the build row, not into `lets-build`.** The build row reads: on `lets-standard`, first run the `lets-review-plan` skill on the change `<name>`. With no **Plan review** section in the pull request it reviews the plan. Otherwise its *Check an earlier review* decides, and it runs its own rounds. Run `lets-build` only when the review is finished. On any other schema, run `lets-build` at once. Stop when every task is ticked. The prompt frame already turns a stop that needs the user into a `needs-input` report, so the two-`REVISE` stop needs no new rule. `lets-go`'s reads and lines for review plan do not change: it still runs inside build. #186 moves this text into a row of its own. Alternative: leave the gate in `lets-build`'s *Apply*. Rejected: `lets-build` is the build step, and #186 would then edit `lets-build` to take the gate out again.
6. **`lets-review-build` finishes on every flow and ships in both.** Its *Start* gains the read `lets-build`'s *Finish the change* made: the `schema:` line of `openspec/config.yaml`, the flow's schema. On `lets-standard` it reads the pull request's body and reviews as today, then finishes. On any other schema it goes straight to *Finish the change*. Its description and first line say it ends a change, not a change on the standard flow. *Finish the change* opens: finish once *Start* sent you here, which on `lets-standard` means the **Code review** section covers the branch. Its *When to apply* names `lets-go`'s review build step. `flows.json` lists it in `minimal`. The README's flows table keeps `Independent code review | Yes | No`, and its `minimal` *Skills it adds* row gains `lets-review-build`. One gap stays open on purpose: `lets-go`'s *Find the first unfinished step* and *Records that disagree* expect a **Code review** section on every archived change, whatever the flow. That is true today for a `minimal` project too, and #186 owns the records check. The risks name it. Alternative: put the four finishing steps in `lets-go`'s review build row for the `minimal` flow. Rejected: the finish would live in two places, and the row would hold a recipe the step skills hold everywhere else. Alternative: ship `lets-review-build` in `standard` only and have `lets-build` keep a `minimal` finish. Rejected: the packet says `lets-build` stops when every task is ticked.
7. **The rows name the skills; the schemas name the doors.** `lets-go`'s plan row: invoke the `lets-plan` skill for the change `<name>`, for issue #<i>, with the route line; continue the change if it exists; stop when the plan is ready, offer no handoff. Review build row: invoke the `lets-review-build` skill for the change `<name>`. Both schemas' brainstorm step 1 says `lets-go` picked and claimed the story, and that a change starts from the `lets-go` skill. Both apply instructions end: when every task is done, stop; the `lets-review-build` skill finishes the change. `lets-standard`'s apply instruction says the `lets-build` skill runs this step, and that `lets-go` has the plan reviewed with the `lets-review-plan` skill before it. `lets-minimal`'s says only that `lets-build` runs it. `lets-review-plan`'s description and *When to apply* name `lets-go`'s build step. The flow-ships test needs every shipped skill named by a schema, the config or a shipped skill. `lets-go` names `lets-plan`, `lets-build`, `lets-review-plan` and `lets-review-build`, so both flows pass.
8. **Every door that opened onto `lets-build` opens onto `lets-go`.** `overlays/AGENTS.md`: the row `| Start the next story, or move the current branch's change on | The \`lets-go\` skill |`, and the backlog bullet says `lets-go` picks, claims and routes. 9. **ADR-020 supersedes ADR-018 by name and by status.** `docs/decisions/ADR-020-lets-go-is-the-only-runner.md` records one decision: the workflow has one runner, `lets-go`; each step has one skill of its own name; `lets-build` builds and nothing else. ## Risks / Trade-offs

- [A project's agent still runs `lets-build` to start work] → The new description and the default-branch message both say to run `lets-go`. The routing row, `lets-shape`'s handoffs and the README agree.
- [A project on the `minimal` flow gets two new skills] → Both are small, and the finish they give the flow is the one `lets-build` gave it. The proposal marks the shipping change.
- [`lets-go` reports `Records disagree` on an archived `minimal` change, because its pull request has no **Code review** section] → True today as well: `lets-build`'s `minimal` finish wrote no section either. #186 rewrites the records check with the step table, and this plan's design names the gap so #186 does not miss it.
- [The moved sections make `lets-go` long before #187 reads it] → The move is near-verbatim, with five named adaptations, so the diff shows no rewrite. #187 is next but one on the stack.
- [`next` on `lets-go` claims an issue the user did not name] → It is what `lets-build` did on the default branch, with the same rank and the same prerequisite check, and the level still comes from the Kind.
- [Two sessions race on `next`] → *Claim*'s lost-race rule keeps its candidates, so a run that came from *Pick the first ready story* stays under its parent, and the blocker read, *Confirm the packet* and *Route* run again for the new issue.
- [`lets-review-plan` is named by the build row, and the `minimal` flow does not ship it] → The row keys the review on `lets-standard`, which no `minimal` project has. The flow-ships test looks for names only in the other direction.
- [Two scenarios still say `as lets-build does`] → They sit in requirements this change does not touch, and their behaviour does not change. Accepted.
- [`openspec archive` refuses a delta] → `openspec validate --strict` accepts both deltas. The last task rehearses the archive in a throwaway worktree under `.workspace/`, as the earlier layers did.

## Migration & Rollback

No data changes shape. A project upgrades with `lets sync`, which copies `lets-plan`, the trimmed `lets-build` and the moved `lets-go`, and adds `lets-review-build` to a `minimal` project. A user's `delegate.handoff.apply.guidance` stays valid and unused. Rollback is reverting the branch's commits.
