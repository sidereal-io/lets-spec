## Context

`skills/lets-build/SKILL.md` is a runner. On the default branch it finds the issue, confirms its packet, routes it, runs the glossary preflight, claims it, imports the glossary checkpoint and proposes. On a change's branch it continues the plan, applies, or finishes. Its *Propose* offers a handoff through `lets delegate handoff`, its *Apply* has the plan reviewed with `lets-review-plan` on `lets-standard`, and its *Finish the change* invokes `lets-review-build` on the `standard` flow and finishes a `minimal` change itself.

`skills/lets-go/SKILL.md` names six of those sections by name, and repeats none. Its step table has three rows: plan runs `openspec-propose`, build runs `lets-build` and stops short of *Finish the change*, and review build runs that section. Review plan has no row: it runs inside build. `tests/skill-interfaces.bats` pins all of this as text, and the `lets-go` and `issue-comments` specs name `lets-build`'s sections. Both schemas tell the brainstorm that `lets-build` claimed the story, and tell apply to start from `lets-build` and finish through it. The routing tables send "start the next story" to `lets-build`.

`lets-review-build` ships in the `standard` flow only. Nothing else can finish a change on the `minimal` flow once `lets-build` stops at the last tick. #186 will give review plan a session and walk the five steps from one table; #187 will rewrite `lets-go` in plain language. This change is the fourth of the six stacked on #177. The pinned OpenSpec CLI in this repository still lists a `review` artifact, from the 0.7.0 copy of the schema; apply depends on `tasks` alone, so the plan reaches `ready` without it.

## Goals / Non-Goals

**Goals:**
- Each step has one skill of its own name: `lets-plan` plans, `lets-build` builds, `lets-review-build` finishes, in both flows.
- `lets-go` is the only runner. The six sections live in it, unchanged in wording, and no skill names a section of `lets-build`.
- Behaviour on either flow is what it was: the same claim, the same route, the same reviews, the same finish.
- The next story, #186, finds one skill per step row and one gate to move, not three places to edit.

**Non-Goals:**
- A session or report for review plan, the step table, or new skip lines (#186).
- Rewriting the moved sections or the rest of `lets-go` (#187).
- Removing the `handoff` strategy, its commands, its docs or its config key.
- Changing `openspec-propose` or `openspec-apply-change`, the schemas' artifacts, or this repository's synced copies and `openspec/config.yaml`.

## Test Seams

- **Primary test seam:** `tests/skill-interfaces.bats`. It reads the skills, `flows.json`, the overlay, the schemas and the README as text, and checks fixed strings and that every name points at something real. It also builds each flow and checks that the reference links resolve.
- **Existing seams reused:** `tests/sync-rules.bats`, which reads the rules fragment; `tests/release-build.bats` and `nix flake check`, which build both flows from `flows.json`; `tests/openspec-compat.bats`, which runs OpenSpec's CLI over each schema.

## Scrutiny Tier & Blast Radius

- **Tier:** medium
- **Blast radius:** five skills, one new; both schemas' brainstorm and apply instructions; `flows.json`; the overlay; the README; two specs; one new decision record and one status line; two bats files. Outside the repository: every project on either flow. After `lets sync`, "start the next story" runs `lets-go`, `lets-build` builds only, and the `minimal` flow gains `lets-plan` and `lets-review-build`.

## Decisions

1. **`lets-plan` is a thin door to `openspec-propose`.** `skills/lets-plan/SKILL.md` has four parts. *Find where you are*: it runs on a change's branch, `<name>`; the caller gives the issue and the route line, as `lets-go`'s plan prompt does; by hand with neither, it finds the issue with the title search `lets-go` uses, `gh issue list --state open --search "<branch> in:title" --json number,title`, and keeps the one whose title starts with `<branch> — `. *Plan*: invoke the `openspec-propose` skill for `<name>`, for #<i>, with the route line for the proposal's commit message; say to use the schema `lets-minimal` when the route is `lets-minimal` and the flow's schema is not; say to continue the change when it exists. With no change and no route line, stop: `lets-go` routes and claims. *When propose stops*: read `openspec instructions apply --change <name> --json`; `ready` means the plan is ready, and on `lets-standard` the review comes next; anything else means propose stopped early. *Rules*: no handoff, no `lets delegate` command, no build, no artifact written outside the skills it invokes. Alternative: fold the route table into `lets-plan`, so it can start a change by hand. Rejected: routing reads the Project and the parent epic, which is Start's work, and `lets-go` already carries it.
2. **`lets-build` keeps its name and one job.** The skill shrinks to *Find where you are*, *Apply* and *Rules*. It reads `openspec instructions apply --change <branch> --json`. `ready`: invoke the `openspec-apply-change` skill for `<branch>`; the schema's apply instruction works test-first with the `lets-test-first` skill; stop at `all_done` and say the `lets-review-build` skill finishes the change. `blocked`: say the plan is not finished, and to run `lets-plan`. `all_done` on entry: say every task is ticked, and name `lets-review-build`. Any other branch, including the default branch: say that `lets-build` builds a planned change on its branch, and that `lets-go` starts an issue. Nothing else stays: no find, confirm, route, claim, handoff, plan review or finish. Its description changes to match, so an agent that reads descriptions to pick a skill no longer picks it to start work.
3. **The six sections move into `lets-go` word for word.** They become `###` subsections of *Start*, after the numbered steps, in `lets-build`'s order: *Find the source of demand*, *Confirm the packet*, *Route*, *Glossary preflight* with *Check the prerequisite* and *Check the checkpoint* as `####`, *Claim*, *Import the glossary checkpoint* with its two `####` parts. Only three edits touch the moved text. *Claim*'s branch-exists stop says to switch to the branch and run `lets-go` there. *Find the source of demand*'s third case, `next`, keeps its text, and `lets-go` runs it when given nothing (decision 4). The sentence in *Propose* that says the route line goes in the proposal commit stays with *Route*. The numbered steps of *Start* say `Run *Find the source of demand* for <i>` where they said `Run lets-build's *Find the source of demand*`, and the paragraph that says `lets-go` reuses `lets-build` goes. The intro's `Run every command below from the repo root` already covers the moved commands. Alternative: a shared reference file under `skills/lets-go/references/` that both skills link. Rejected: `lets-build` would not read it, and a reference is for a method, not for the steps a skill runs. Alternative: rewrite the sections as they move. Rejected: #187 owns the plain-language pass, and a faithful move keeps this diff reviewable.
4. **`lets-go` with nothing takes `next`.** *Start* step 2 gains a third request form on the default branch: **Nothing** runs the third case of *Find the source of demand*, over the whole backlog, with its rank and *Check the prerequisite* per candidate. It prints `Picked #<n>: <title>, the next ready issue.` and goes on from step 3 with that issue. When nothing is ready, the case's own stop stands: the backlog has nothing ready, run `lets-shape`. The routing row sends "start the next story" to `lets-go`, so this is the one new behaviour the move needs. The ask-or-recommend level comes from the Kind as usual. Alternative: keep the stop that asks for a number or an idea. Rejected: the routing row would point at a skill that cannot start the next story.
5. **The plan review gate moves into the build row, not into `lets-build`.** The build row reads: on `lets-standard`, first run the `lets-review-plan` skill on the change `<name>`; with no **Plan review** section in the pull request it reviews the plan, otherwise its *Check an earlier review* decides, and it runs its own rounds; run `lets-build` only when the review is finished; on any other schema, run `lets-build` at once; stop when every task is ticked. The prompt frame already turns a stop that needs the user into a `needs-input` report, so the two-`REVISE` stop needs no new rule. `lets-go`'s reads and lines for review plan do not change: it still runs inside build. #186 moves this text into a row of its own. Alternative: leave the gate in `lets-build`'s *Apply*. Rejected: `lets-build` is the build step, and #186 would then edit `lets-build` to take the gate out again.
6. **`lets-review-build` finishes on every flow and ships in both.** Its *Start* gains the read `lets-build`'s *Finish the change* made: the `schema:` line of `openspec/config.yaml`, the flow's schema. On `lets-standard` it reads the pull request's body and reviews as today, then finishes. On any other schema it goes straight to *Finish the change*. Its *When to apply* names `lets-go`'s review build step. `flows.json` lists it in `minimal`. The README's flows table keeps `Independent code review | Yes | No`, and its `minimal` *Skills it adds* row gains `lets-review-build`. Alternative: put the four finishing steps in `lets-go`'s review build row for the `minimal` flow. Rejected: the finish would live in two places, and the row would hold a recipe the step skills hold everywhere else. Alternative: ship `lets-review-build` in `standard` only and have `lets-build` keep a `minimal` finish. Rejected: the packet says `lets-build` stops when every task is ticked.
7. **The rows name the skills; the schemas name the doors.** `lets-go`'s plan row: invoke the `lets-plan` skill for the change `<name>`, for issue #<i>, with the route line; continue the change if it exists; stop when the plan is ready, offer no handoff. Review build row: invoke the `lets-review-build` skill for the change `<name>`. Both schemas' brainstorm step 1 says `lets-go` picked and claimed the story, and that a change starts from the `lets-go` skill. Both apply instructions end: when every task is done, stop; the `lets-review-build` skill finishes the change. `lets-standard`'s apply instruction says the `lets-build` skill runs this step, and that `lets-go` has the plan reviewed with the `lets-review-plan` skill before it. `lets-minimal`'s says only that `lets-build` runs it. `lets-review-plan`'s description and *When to apply* name `lets-go`'s build step. The flow-ships test needs every shipped skill named by a schema, the config or a shipped skill: `lets-go` names `lets-plan`, `lets-build`, `lets-review-plan` and `lets-review-build`, so both flows pass.
8. **The routing tables and the README send the next story to `lets-go`.** `overlays/AGENTS.md`: the row `| Start the next story, or move the current branch's change on | The \`lets-go\` skill |`, and the backlog bullet says `lets-go` picks, claims and routes. The README: the usage row `| Start the next story, or carry on the change on your current branch | \`lets-go\` |`; the intro names `lets-shape` and `lets-go` as the skills you talk to, and the four step skills as ones to run alone; the `lets-build` section becomes *The step skills*, a four-row table, one line per skill; the `lets-go` section says it claims the issue itself and takes the next ready issue when given nothing, and names no `lets-build`; the packet, Project fields and blocker texts name `lets-go`; the working rules say only `lets-shape` and `lets-go` set Project fields; the quick start says `lets-go` builds the first story; the reviews section opens with reviews alone. `docs/backlog-adapter-contract.md` names `skills/lets-go/SKILL.md` in its baseline where it named `lets-build`.
9. **ADR-020 supersedes ADR-018 by name and by status.** `docs/decisions/ADR-020-lets-go-is-the-only-runner.md` records one decision: the workflow has one runner, `lets-go`; each step has one skill of its own name; `lets-build` builds and nothing else. Its blockquote names ADR-018 as the record it supersedes, and ADR-018's `status:` becomes `superseded by ADR-020`, as ADR-003's did for ADR-010. The alternatives are ADR-018's choice, retiring `lets-build` into `lets-go`'s prompt, and keeping two runners. The ADR step writes it.
10. **The specs rename one requirement and keep scenario headings.** The `lets-go` delta renames *Start reuses lets-build* and modifies ten requirements; the `issue-comments` delta modifies four. Scenario headings keep their names, because the validator refuses a `MODIFIED` block whose scenario names differ; their WHEN and THEN carry the new names. Two scenarios in requirements this change does not modify still say `as lets-build does`; they are labels on behaviour that does not change, and #187 or a later change can retouch them.
11. **The tests pin the new shape from both sides.** In `tests/skill-interfaces.bats`: the handoff pins and `hold the prompt to carry on by hand` go; the gate test reads `lets-go` for `schema: lets-standard`, `` `lets-review-plan` skill `` and `*Check an earlier review*` beside `` `lets-build` skill ``; the `finish_section` helper reads `lets-review-build`'s *Start* for `openspec/config.yaml` and `` `lets-standard` ``; the sessions pin goes; the Start test checks the six headings in `lets-go` and that `gh project item-edit` is there; the `first_gh` pattern drops `lets-build. does`; the issue-comments link, the watermark sentence, the link resolution and the vocabulary loop read `lets-go`; the guidance pin's list drops `lets-build`. New: `lets-plan` says `` `openspec-propose` skill `` and `openspec instructions apply --change <name> --json` and not `lets delegate`; `lets-build` says `` `openspec-apply-change` skill `` and `` `lets-test-first` skill `` and holds no `Finish the change`, `gh project`, `lets delegate`, `lets-review-plan` or `Find the source of demand`; no file under `skills/`, `schemas/` or `overlays/` says `` `lets-build`'s * ``; both flows ship `lets-plan` and `lets-review-build`; both tables hold their next-story row and no row that names `lets-build`; `lets-go` says `Picked #<n>: <title>, the next ready issue.`; the README's `minimal` *Skills it adds* row names `lets-review-build`. In `tests/sync-rules.bats`, the rules block says `lets-go` picks, claims and routes, and does not say `lets-build`.

None of these is costly to reverse on its own. Where the runner lives, in `lets-go` rather than in two skills, is the fork many readers bind to, and it reverses a recorded decision. The ADR step records it.

## Risks / Trade-offs

- [A project's agent still runs `lets-build` to start work] → The new description and the default-branch message both say to run `lets-go`. The routing row and the README agree.
- [A project on the `minimal` flow gets two new skills] → Both are small, and the finish they give the flow is the one `lets-build` gave it. The proposal marks the shipping change.
- [The moved sections make `lets-go` long before #187 reads it] → The move is word for word, so the diff shows no rewrite, and #187 is next but one on the stack.
- [`next` on `lets-go` claims an issue the user did not name] → It is what `lets-build` did on the default branch, with the same rank and the same prerequisite check, and the level still comes from the Kind.
- [`lets-review-plan` is named by the build row, and the `minimal` flow does not ship it] → The row keys the review on `lets-standard`, which no `minimal` project has. The flow-ships test looks for names only in the other direction.
- [Two scenarios still say `as lets-build does`] → They sit in requirements this change does not touch, and their behaviour does not change. Accepted.
- [`openspec archive` refuses a delta] → `openspec validate --strict` accepts both deltas. The last task rehearses the archive in a throwaway worktree under `.workspace/`, as the earlier layers did.

## Migration & Rollback

No data changes shape. A project upgrades with `lets sync`, which copies `lets-plan`, the trimmed `lets-build` and the moved `lets-go`, and adds `lets-review-build` to a `minimal` project. A user's `delegate.handoff.apply.guidance` stays valid and unused. Rollback is reverting the branch's commits.
