## Story

#185 lets-plan-and-lets-build — lets-plan is the plan step and lets-build
is the build step; find, confirm, route and claim move into lets-go, and
a decision record supersedes ADR-018.
https://github.com/sidereal-io/lets-spec/issues/185

## Decisions

| # | Question | Answer | Source |
|---|---|---|---|
| D1 | What does `lets-plan` do? | It is a new skill, `skills/lets-plan/SKILL.md`, and runs on a change's branch, `<name>`. Its caller gives it the issue and the route line, as `lets-go`'s plan prompt does. Run by hand with neither, it finds the issue by the branch's title search, `gh issue list --state open --search "<branch> in:title"`, as `lets-go` does. It invokes the `openspec-propose` skill for `<name>`, for #<i>, with the route line for the proposal's commit message. When the route is `lets-minimal` and the flow's schema is not, it says to use that schema. When the change exists, it continues it. When no change exists and it has no route line, it stops and says that `lets-go` routes and claims the issue. | Evidence: #185 packet, Scope; `skills/lets-go/SKILL.md`, the plan row |
| D2 | Where does `lets-plan` stop? | When propose is done, it reads `openspec instructions apply --change <name> --json`. `ready` means tasks.md is committed: it says the plan is ready, and on `lets-standard` that review plan comes next. It offers no handoff and runs no `lets delegate handoff` command. Any other state means propose stopped early: it says so, and stops. | Evidence: #185 packet, "stops when tasks.md is committed, with no handoff offer" |
| D3 | What does `lets-build` become? | The build step only. On a change's branch it reads the same `openspec instructions apply` state. `ready`: it invokes the `openspec-apply-change` skill for `<branch>`, whose apply instruction works each task test-first with the `lets-test-first` skill. It stops when every task is ticked, `all_done`, and says the `lets-review-build` skill finishes the change. `blocked`: it says the plan is not finished, and to run `lets-plan`. `all_done` on entry: it says every task is ticked, and names `lets-review-build`. Any other branch: it says it works on a change's branch. It finds, claims, routes, reviews and finishes nothing. | Evidence: #185 packet, Scope |
| D4 | Who finishes a change on the `minimal` flow, now that `lets-build` loses *Finish the change*? | `lets-review-build` ships in both flows and takes the read that *Finish the change* made. Its *Start* reads the `schema:` line of `openspec/config.yaml`, the flow's schema. On `lets-standard` it reviews the code, then finishes. On any other schema it goes straight to *Finish the change*. Behaviour does not change: the `standard` flow reviews, the `minimal` flow does not. This revisits #184's choice to ship the skill in `standard` only; its design left that to the story that gives review build a session, and this story needs it first, because the section it moves is the only finish the `minimal` flow has. | Assumption |
| D5 | Where does the plan review gate go, now that `lets-build`'s *Apply* loses it? | Into `lets-go`'s build row, until #186 gives review plan a session of its own. The row says: on `lets-standard`, first run the `lets-review-plan` skill on the change; with no **Plan review** section it reviews, otherwise its *Check an earlier review* decides. Go on to `lets-build` only when the review is finished. Review plan still runs inside build, with no prompt and no report, so `lets-go`'s reads and lines stand. `lets-review-plan`'s description and *When to apply* name `lets-go`'s build step instead of `lets-build`. | Assumption |
| D6 | What moves into `lets-go`? | Six sections, word for word, as subsections of *Start*: *Find the source of demand*, *Confirm the packet*, *Route*, *Glossary preflight* with its two parts, *Claim* and *Import the glossary checkpoint*. *Start*'s steps say `Run *Claim*` where they said `Run lets-build's *Claim*`, and the sentence that `lets-go` reuses `lets-build` goes. *Claim* keeps `gh project item-edit`, so `lets-go` now sets the Status itself. `lets-build`'s *Find where you are* table goes: `lets-go` has its own reads. Nothing in the moved text is rewritten; #187 owns the plain-language pass. | Evidence: #185 packet, Scope; #148 Shared decisions, revised 2026-11-04 |
| D7 | What does `lets-go` do with no issue number and no idea on the default branch? | It takes `next`, the third case of *Find the source of demand*, over the whole backlog, as `lets-build` did. It prints `Picked #<n>: <title>, the next ready issue.` and goes on from the blocker read with that issue. Today it stops and asks for a number or an idea. The routing row "Start the next story" now points at `lets-go`, so `lets-go` must be able to start the next story. | Assumption |
| D8 | What does `lets-go` say after a failed step? | To run `lets-go` again on the branch `<name>`: it reads the records and goes on from the first unfinished step. Today it says to run `lets-build` there, which no longer carries a change on. | Assumption |
| D9 | What do the routing tables and the README say? | `overlays/AGENTS.md`: the row `Start the next story, or move the current branch's change on` points at `lets-go`, and the backlog bullet says `lets-go` picks, claims and routes. `README.md`: the same usage row; the intro names `lets-shape` and `lets-go` as the skills you talk to, and the four step skills as ones you can run alone; the `lets-build` section becomes a short section on the step skills, `lets-plan`, `lets-review-plan`, `lets-build` and `lets-review-build`, one line each; the `lets-go` section says it claims the issue itself and takes `next` when given nothing; the Project fields text and the blocker note name `lets-go`; the working rules say only `lets-shape` and `lets-go` set Project fields; the quick start says `lets-go` builds the first story; the reviews section no longer says builds hand off. `docs/backlog-adapter-contract.md` names `skills/lets-go/SKILL.md` where it named `lets-build` as a reader of the backlog. | Assumption |
| D10 | What does `flows.json` ship? | `lets-plan` in both flows, after `lets-go`. `lets-review-build` in both flows (D4). The fixture in `tests/support/release.bash` stands. | Evidence: #185 packet, Scope; D4 |
| D11 | What do the schemas say? | Both brainstorm instructions: `lets-go` picked and claimed the story, and a change starts from the `lets-go` skill. Both apply instructions: the `lets-build` skill runs this step, and when every task is done, stop, because the `lets-review-build` skill finishes the change. `lets-standard`'s apply instruction adds that `lets-go` has the plan reviewed with the `lets-review-plan` skill before it. The pinned copies under `openspec/schemas/` are not touched. | Assumption |
| D12 | What does the decision record say? | ADR-020, "lets-go is the only runner, and lets-build is the build step", supersedes ADR-018. One decision: the workflow has one runner, each step has one skill of its own name, and `lets-build` builds and nothing else. Its alternatives are ADR-018's choice, keeping `lets-build` as the in-session runner beside `lets-go`; retiring `lets-build` and putting apply in `lets-go`'s prompt; and keeping both runners. ADR-018's status becomes `superseded by ADR-020`, as ADR-003's did for ADR-010. | Evidence: #148 Shared decisions, revised 2026-11-04; `docs/decisions/ADR-003-one-resolver-per-harness.md`, its status line |
| D13 | Which main specs change? | `lets-go`: *Start reuses lets-build* is renamed *Start finds, confirms, routes and claims the issue* and modified; modified too are *Review plan is reported as not in the route* (D5), *The step prompt says what to run, the level, and how to report* (D1, D5, D4), *A run ends on done, failed, or a repeated question* (D8), *Review build ends the run* (D4), *lets-go finds the first unfinished step*, *lets-go runs for a Chore, a Bug or a Story*, *lets-go takes one issue number or an idea* (D7), *lets-go picks the first ready story* and *lets-go ships in both flows as an entry point* (D9, D10). `issue-comments`: the four requirements that name `lets-build`'s *Confirm the packet* and `skills/lets-build/SKILL.md` name `lets-go` instead. Scenario headings keep their names, as the step-names change found the validator requires. No spec covers `lets-plan`, `lets-build`, the schemas, the overlay or the README: the bats tests pin them. | Evidence: `openspec/specs/lets-go/spec.md`; `openspec/specs/issue-comments/spec.md`; `openspec/changes/archive/2026-11-04-step-names/design.md`, decision 4 |
| D14 | What do the tests pin? | `tests/skill-interfaces.bats`: the handoff pins and the sentence about carrying on by hand go; the plan review gate is pinned in `lets-go`'s build row; the finish pins read `lets-review-build`'s *Start* for `openspec/config.yaml` and `lets-standard`; `lets-go` holds the six sections as headings and now holds `gh project item-edit`; the issue-comments link, the watermark sentence and the vocabulary check move from `lets-build` to `lets-go`; new pins say `lets-plan` names the `openspec-propose` skill and no `lets delegate handoff`, `lets-build` names the `openspec-apply-change` and `lets-test-first` skills and holds no `Finish the change`, `gh project` or `lets delegate`, both routing tables hold the new row, both flows ship `lets-plan`, and no skill, schema or overlay names a section of `lets-build`. `tests/sync-rules.bats`: the rules block names `lets-go` as the skill that picks, claims and routes, and not `lets-build`. | Assumption |
| D15 | Does the glossary change? | No. *Step* still says review plan runs inside build until it has a session of its own, which stays true (D5). | Evidence: `openspec/glossary.md` |
| D16 | What stays out? | The `handoff` strategy in `lets`, with `docs/resolvers.md`, the README's handoff term and its config example; what `openspec-propose` and `openspec-apply-change` do; the step table, the review plan session and the skip lines of #186; the plain-language pass of #187; this repository's synced copies in `.agents/skills/` and `openspec/schemas/`, and its `openspec/config.yaml`; archived changes and earlier decision records beyond ADR-018's status line. | Evidence: #185 packet, out; #186 and #187 packets |
