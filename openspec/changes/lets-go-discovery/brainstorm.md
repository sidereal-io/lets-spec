## Story

#154 lets-go-discovery — a large idea runs discovery first, then lets-go carries on with the first ready story. https://github.com/sidereal-io/lets-spec/issues/154

The user delegated this brainstorm to the orchestrating session on 2026-11-04 and asked for a recommendation on every question. Each recommendation is recorded as an `Assumption`, so the plan review checks it. The issue has no comments. The packet was last edited on 2026-11-04.

## Decisions

| # | Question | Answer | Source |
|---|---|---|---|
| D1 | Who tells a large idea from a single issue? | The shape step, as `lets-shape` does today. Its *Shape one issue* sizes the work at step 6, and its mode pick says an issue that holds a large idea is a discovery input. Start keeps no size check of its own. | Evidence: `skills/lets-shape/SKILL.md` (Locate the discovery, step 4; Shape one issue, step 6) |
| D2 | Is discovery a decision the step takes, or a question? | A question. `lets-shape` offers discovery; it does not start one unasked. So the step ends its round with a `needs-input` question, `The work is Size <L or XL>, too large for one issue. Run discovery on it?`, with the recommendation `yes`. At `recommend`, `lets-go` accepts it; at `ask`, the user answers. On yes, the resumed step runs discovery. On any other answer, the step ends `failed`, saying the work is too large for one issue and discovery was declined. This replaces the `failed` report that #153 gave a too-large idea. | Evidence: ADR-015; `skills/lets-shape/SKILL.md` (Shape one issue, step 6); Assumption |
| D3 | Is discovery its own step? | No. It is a path inside the `shape` step, which runs at most once per run, keeps its `--name`, `issue-<i>` or `idea-<slug>`, and its answers file. The epic says `lets-shape` is the skill behind the shape step, and the packet says the shape step tells a large idea from a single issue. | Evidence: #148 Shared decisions; #154 Scope; Assumption |
| D4 | What does the step run for a large idea? | `lets-shape`'s discovery, every phase from Ingest to Finalize, with the idea or #<i> as its input, through the glossary handoff and the Finalize handoff text. Each phase's confirmation, and the story table in Phase 5, is a confirmation question with no recommendation. The step creates no change and no change branch. The parent issue, the stories, and a glossary holding branch are `lets-shape`'s own. | Evidence: `skills/lets-shape/SKILL.md` (The phases); Assumption |
| D5 | How does a resumed round find the discovery? | Through `lets-shape`'s own checkpoints. Every confirmed phase is written to the parent issue and `discovery.md`, and the parent's status line names the next phase. The prompt says that an open parent issue that says `Discovery status: in-progress` and names this input is resumed, as *Resume mode* says. The answers file carries every earlier answer, so a resumed round asks nothing twice. | Evidence: `skills/lets-shape/SKILL.md` (The phases; Resume mode); ADR-017; Assumption |
| D6 | How does the report name the parent and the stories? | A done report's first evidence line is `epic #<p>: <title>`, then one line per story, `story #<n>: <title>`, in the order created. For one issue it stays `issue #<n>: <title>`. When Phase 5 finds that the whole run fits one story, the parent becomes that story, and the report takes the `issue` form. A first line in neither form, or an `epic` line with no `story` line, is a `failed` report whose reason says the shape step named no issue or no story. | Evidence: `skills/lets-shape/SKILL.md` (Phase 5, one story or many); Assumption |
| D7 | How does `lets-go` pick the story? | By naming `lets-build`'s *Find the source of demand*, its third case, `next`, with one narrowing: the candidates are the report's stories, not the whole backlog. Its two commands run as written, its rank is Must, Should, Could, then the lowest number, and *Check the prerequisite* runs on each candidate in rank order. The first story in dependency order is the walking skeleton, with no blocker, so it is the usual pick. A `next` over the whole backlog could pick an unrelated Must, which is not what the user asked for. | Evidence: `skills/lets-build/SKILL.md` (Find the source of demand, case 3); #148 Shared decisions; Assumption |
| D8 | What does `lets-go` print when it picks? | `Picked #<n>: <title>, the first ready story under #<p>.` Then Start goes on from step 3 with `<i>` as the story, as for an issue number. The shape line is `Done shape: <date>. <evidence>`, whose evidence names the epic and the stories. | Assumption |
| D9 | What happens when no story is ready? | `lets-go` prints the `Done shape` line, says no story under #<p> is ready, names each story and why it was skipped, says to run `lets-go` with a story's number once it is ready, and stops. There is no branch. | Evidence: `skills/lets-build/SKILL.md` (`next`, the empty case); Assumption |
| D10 | Where do the map's edits go? | Discovery edits `openspec/discovery.md` in the working tree on the default branch, and nobody commits there. So the shape step ends on the default branch with the tree clean except `openspec/discovery.md`, when discovery ran. After *Claim* creates the story's branch, `lets-go` commits that file alone on it as `docs: the discovery map from #<p>`, before *Find the first unfinished step* reads the tree. When the run stops before *Claim*, `lets-go` says the map is uncommitted on the default branch. This is the one commit `lets-go` makes itself, beside the glossary import. | Evidence: `git log -- openspec/discovery.md` (committed by hand so far); `skills/lets-go/SKILL.md` (Find the first unfinished step, the tree); Assumption |
| D11 | Who owns glossary edits made in discovery? | `lets-shape`'s glossary handoff asks, as it does today, and the question reaches the user through the relay. The prompt recommends the first story in dependency order as the owner. When another story owns them, *Check the prerequisite* skips the picked candidate until that owner merges, as `next` does. | Evidence: `skills/lets-shape/SKILL.md` (Glossary handoff); `skills/lets-build/SKILL.md` (Check the prerequisite); Assumption |
| D12 | Which level does discovery run at? | The shape step's: the user's when named, else `ask`. The confirmations ask at either level. After the pick, step 10 sets the level again from the story's Kind, as today. | Evidence: `openspec/specs/lets-go/spec.md` (lets-go picks the interactivity level); Assumption |
| D13 | What about an existing issue that holds a large idea? | The same path. The step shapes #<i>, judges it too large, asks, and runs discovery with #<i> as the input. Phase 1 reads its thread and replies. The input issue stays open, as `lets-shape` leaves it; `<i>` becomes the picked story. | Evidence: `skills/lets-shape/SKILL.md` (The input is read-only; Phase 1); Assumption |
| D14 | Do `lets-build` or `lets-shape` change? | No. `lets-go` names `lets-build`'s `next` case and narrows its candidates; `lets-shape`'s discovery runs as it is inside the step, and its phase confirmations reach the user through the relay. | Evidence: `skills/lets-build/SKILL.md`; `skills/lets-shape/SKILL.md` |
| D15 | What changes in files? | `skills/lets-go/SKILL.md`: the description, the `shape` row, *Run the shape step* (the pick, the map commit, the none-ready stop), *Read the report* (the `epic` and `story` lines) and the README's `lets-go` section. `openspec/specs/lets-go/spec.md`: the shape step requirement and the step prompt requirement, one new requirement for discovery and the pick, and the fixed strings; its `## Purpose`, edited directly. `tests/skill-interfaces.bats`: the new fixed strings, and the too-large phrase that must go. `overlays/AGENTS.md` and `flows.json` are unchanged: the routing row already says an idea in words. | Evidence: #154 packet; `tests/skill-interfaces.bats` |
| D16 | New glossary terms? | None committed. *Discovery* keeps `lets-shape`'s meaning, the phases from Ingest to Finalize, and *ready* keeps `next`'s meaning: Todo, a Priority, nobody assigned, nothing blocking it, and no unresolved prerequisite. The skill says both in words where it uses them. | Assumption |
| D17 | Can it run here now? | No. The pinned `lets` 0.7.0 has no `step` command. The tests check the skill's prose, as in #149, #150, #152 and #153. | Evidence: `mise.toml` |
