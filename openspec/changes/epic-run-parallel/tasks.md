## 1. `lets delegate step start` and `step wait`

The two commands go in a new module, `lets/src/delegate/background.ts` (design D-A to D-C). Its tests go in a new `tests/lets/delegate/background.test.ts`, driven through `tests/lets/delegate/fixtures/command-deps.ts`, whose fake `Io` gains `spawnDetached`, `isAlive` and `sleep`, records each spawn and holds the run files in memory. Each scenario of the `delegate-step` delta in `openspec/changes/epic-run-parallel/specs/delegate-step/spec.md` is one test. Run records and exit files go in `.workspace/lets-delegate/` of the repository root where `step start` ran.

- [x] 1.1 [medium] `lets delegate step run` takes a hidden `--exit-file <path>`, not shown in its help: once the command's exit code is known, including 2 from a usage error that `guarded` caught, `lets/src/main.ts` writes `{"exit":<code>,"endedAt":<ms>}` to that file, then exits (design D-B). A test in `tests/lets/delegate/step.test.ts` checks the file after a `done` report (exit 0) and after an unreadable prompt file (exit 2), and that `step run --help` does not name `--exit-file` (verify: node --test tests/lets/delegate/step.test.ts) (✓ node --test tests/lets/delegate/step.test.ts passed)
- [x] 1.2 [complex] `step start` in `background.ts` takes the options of `step run` plus the required `--report-file` and `--meta-file` and the optional `--checkout`. It checks them and reads the prompt and answers files first, exiting 2 with nothing started on a missing option or an unreadable file. It resolves every path against its working directory, writes `.workspace/lets-delegate/<name>.run.json` (`name`, `pid`, `checkout`, `reportFile`, `metaFile`, `exitFile`, `startedAt`), and calls `Io.spawnDetached` with the running Node binary and `lets` entry, the arguments `delegate step run`, the options of `step run` it was given with each path made absolute, and `--exit-file` with the exit file's absolute path, but not `--checkout`, `--report-file` or `--meta-file`, the checkout's repository root as working directory, and stdout and stderr on the report and meta files. It prints `{"name":"<normalized name>","pid":<pid>}` and exits 0. It exits 2, naming the step and its `pid`, when a run of the same name has a run record, no exit file and a live `pid`, and accepts the name again once that run has ended. The scenarios of *step start runs a step in the background* (help aside) and *step start refuses a name that is still running* pass (verify: node --test tests/lets/delegate/background.test.ts) (✓ node --test tests/lets/delegate/background.test.ts passed)
- [x] 1.3 [complex] `step wait --name <name>...` in `background.ts` reads each named run record, exiting 2 with empty stdout and the name on stderr when one has none. Every 2 seconds, through `Io.sleep`, it checks each name for an exit file or a `pid` that `Io.isAlive` says is gone. Once one or more have ended, it prints `{"name":"<name>","exit":<code>}` for the one with the earliest `endedAt`, and exits 0. A dead `pid` with no exit file counts as exit 4, ended when found, and appends `lets delegate: the background step ended without an exit code` to that step's meta file. With `--timeout-minutes`, it exits 6 with empty stdout at the deadline, through the fake clock. The scenarios of *step wait names the next background step to end*, *step wait reports a background step that ended without an exit code* and *step wait's exit codes* (help aside) pass (verify: node --test tests/lets/delegate/background.test.ts) (✓ node --test tests/lets/delegate/background.test.ts passed)
- [x] 1.4 [medium] `lets/src/main.ts` adds `step start` and `step wait` under `lets delegate step`, `lets/src/io.ts` gives the real `Io` `spawnDetached` (a detached `spawn` with its stdout and stderr opened on the files, then `unref`), `isAlive` (`process.kill(pid, 0)`) and `sleep`. `step start --help` names `--checkout`, `--report-file` and `--meta-file`, lists exit codes 0 and 2, and says `step wait` tells when the step ends; `step wait --help` lists 0, 2 and 6 and says the report is in the report file given to `step start`. A test in `tests/lets/delegate/cli.test.ts` runs the real `lets/bin/lets` in a temporary git repository with only the `subagent` resolver: `step start --for plan` returns at once, and `step wait` then prints `{"name":"<name>","exit":3}` (verify: node --test tests/lets/delegate/cli.test.ts && npx tsc --noEmit) (✓ node --test tests/lets/delegate/cli.test.ts && npx tsc --noEmit passed)

## Deviations Ledger

- 1.1: `run` in `lets/src/delegate/step.ts` writes the exit file, not `lets/src/main.ts`. It is the first place the exit code is known, after `guarded`, and the tests reach it through the fake `Io`, so they can check a `done` report without a real model. `main.ts` only declares the hidden `--exit-file` option.
- 1.2: `Io` gains a fourth method, `letsCommand`, which gives the running Node binary, its flags and the `lets` entry, so `background.ts` makes no process access of its own. The real `Io`'s `spawnDetached`, `isAlive`, `sleep` and `letsCommand` came in this task, not 1.4, so the type check passes at each commit. `step start` also exits 4 when the process cannot start, and creates the folders of the report and meta files.
- 1.3: when `step wait` finds a step whose process is gone with no exit file, it also writes that step's exit file, with exit 4. A later wait then names the step with exit 4 again without adding a second line to its meta file.
- 2.1: the worktree steps for a started story, and the `lets sync` that prepares every worktree, live in a new subsection of *Enter the branch*, *The story's worktree*, after its `Next:` line. The test `stack: Claim creates a stacked story's branch off its blocker's branch with no upstream` now checks `git worktree add --no-track -b`, because a stacked story is created only in an epic run, which no longer switches its checkout.
- 2.3: five existing tests pinned text this task changes, and now check the new text: `an epic run picks each story as next picks it` (the `--exclude` sentence), `an epic run settles a built story with its pull request's URL` (it no longer checks for `git switch <default>`, and its name drops "then switches to the default branch"), and the three `story run:` tests on the story prompt, the `rm -f` of answers and rounds, and the child's command. The two tests that let `lets delegate step` be followed only by `instructions` or `run` now also allow `step start` and `step wait`. *Start the story run* keeps the child's exit codes as its last action until 2.4 moves them to *Wait for the wave*.
- 2.4: *Wait for the wave* is a `###` subsection of *Run the epic* in `references/epic-run.md`, beside *Settle a story*, so it reads as part of the epic run's loop. A story kept for a walk moves to the end of the children file, so the walks keep the order the children ended in. The walk takes the story's schema, route line, question mode and stack from its story prompt, because later picks have set them for other stories since. Two `story run:` tests now read *Wait for the wave* in place of *Start the story run*: the one on the exit-3 walk and the one on a `needs-input` report.
- 2.5: the relay takes `<mode>` from the story's prompt file, because a later pick may have set another story's mode since. A `lets delegate step start` that fails when the child starts again stops the story, as it does in *Start the story run*.
