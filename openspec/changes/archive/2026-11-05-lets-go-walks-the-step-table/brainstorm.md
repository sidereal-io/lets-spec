## Story

#186 lets-go-walks-the-step-table — lets-go runs the five steps from one
table, review plan in a session of its own, and every line it prints
names the step's skill.
https://github.com/sidereal-io/lets-spec/issues/186

## Decisions

| # | Question | Answer | Source |
|---|---|---|---|
| D1 | What is the step table? | One table in `lets-go`, with one row per step in order: shape, plan, review plan, build and review build. Its columns are Step, Skill, Done when, Record and Skip line. *Write the prompt* reads the Skill column, the walk reads Done when, and the skip lines read Record. The two build rows and the *What to run* table go. | Evidence: #186 packet, Scope; #148 Shared decisions, revised 2026-11-04 |
| D2 | How does `lets-go` run the steps? | It walks the table from the top. When it reaches a row, it reads that row's record. A done step prints its `Skipped` line. An unfinished step runs, as *Run a step* says, and a `done` report prints its `Done` line. The walk goes on to the next row until a step fails or the table ends. Then *End of the run* prints the pull request's URL. Done is read when the row is reached, not up front, because a step run in this round changes the records the next row reads. | Assumption |
| D3 | When is review plan done? | On `lets-minimal`, with plan: it is not in the route. On any other schema, when the pull request's **Plan review** section covers the plan: `lets-review-plan`'s *Check an earlier review* finds no reason to run again, and says the review is finished. So a `ready` change with no section, a `REVISE` verdict, a reviewed commit off the branch, or a plan commit after it that no rebuttal names, means review plan runs, not build. `lets-go` reads the body with `gh pr view <name> --json number,body` when it reaches the row. | Evidence: #186 packet, Scope; `skills/lets-review-plan/SKILL.md`, *Check an earlier review* |
| D4 | What does the review plan step look like? | A step like the others: `--for review-plan`, `--name <name>-review-plan`, its prompt from the frame, its report read, its questions relayed. Its session runs the `lets-review-plan` skill, which reviews the plan or lets *Check an earlier review* decide, runs its own rounds, and records in the pull request. A `done` report's first evidence line is `Plan review: <verdict> for <sha>`, then any fix commits and the pull request. Its two-`REVISE` stop comes back as a `needs-input` report. Its line is `Done review plan: <date>. <evidence>`, like every other step's. The line `lets-go` built from the section after build goes. | Evidence: #186 packet, Scope; #148 Shared decisions, revised 2026-11-04 |
| D5 | What does the build row run? | The `lets-build` skill, on every schema. The plan review gate leaves the build row: the review plan row holds it. | Evidence: `openspec/changes/archive/2026-11-04-lets-plan-and-lets-build/design.md`, decision 5 |
| D6 | What does a step prompt say to run? | One sentence for every step, from the Skill column. It says to invoke the `<skill>` skill for the change `<name>`, for issue #<i>, and to stop where that skill stops. The frame's second line gains `Route: <route line>`, which `lets-plan` puts in the proposal commit and the other skills ignore. Shape keeps its own text. The step skills say where they stop, so the rows carry no recipe. | Assumption |
| D7 | Which record dates each skip line? | Plan: the commit that added `openspec/changes/<name>/tasks.md`. Review plan: the section's `Reviewed:` commit, dated with `git log -1 --format=%as <sha>`. Build: the last commit that changed `tasks.md`. Review build: the commit that added the archive folder's `tasks.md`, and the pull request. Shape: the packet's last edit. The reads do not change. | Evidence: #186 packet, Scope; #148 Shared decisions |
| D8 | When is review build done, and what does its line say? | When the archive folder exists and the pull request is ready for review. A **Code review** section is required only when the flow's schema is `lets-standard`, because `lets-review-build` reviews code by the flow, not by the change. The line is `Skipped review build: archived <date> (<sha>); pull request #<p> is ready for review.` on every flow. This closes the gap #184 and #185 left to this story. | Assumption |
| D9 | Which disagreements change? | The archive row requires a **Code review** section only on the `lets-standard` flow. The row for a built change with no **Plan review** section goes: the walk reaches review plan first and runs it. The other rows stand. | Assumption |
| D10 | Does the shape row change? | No. Shape runs inside *Start*, is done when *Confirm the packet* passes, and prints the same line. Its row names `lets-shape` and the packet's last edit. | Evidence: `skills/lets-go/SKILL.md`, *Start* step 5 |
| D11 | Does each printed step line name the step's skill? | No. The title's clause is met by the table and the prompt: every row names its skill, and every prompt invokes it by name. The printed lines keep their pinned forms. Renaming them would touch six more spec requirements and every test string for no new behaviour, and the packet's Scope does not list it. | Assumption |
| D12 | What prints after a failed step? | `Failed <step>: <reason>`, then the branch, and that `lets-go` on it carries on. The rows before it have printed their lines, so a failed build on `lets-standard` prints review plan's line before `Failed build:`. This settles the gap the plan-review-in-the-pull-request review left open. | Evidence: `openspec/changes/archive/2026-11-04-plan-review-in-the-pull-request/review.md`, finding 3 |
| D13 | What else says review plan runs inside build? | `lets-go`'s description and intro. `lets-review-plan`'s description and *When to apply*, which now name `lets-go`'s review plan step. The README's `lets-go` section. The glossary's *Step*, which loses its "until review plan gets a session of its own" sentence. The schemas do not change: `lets-standard`'s apply instruction still says `lets-go` has the plan reviewed first. | Assumption |
| D14 | Which specs change? | `lets-go` only. Two requirements are renamed and modified. *lets-go finds the first unfinished step* becomes *lets-go walks the step table*. *Review plan is reported as not in the route* becomes *Review plan runs as a step, or is not in the route*. Eight more are modified: *Start finds, confirms, routes and claims the issue*, for its command list; *Each step runs through lets delegate step*; *The step prompt says what to run, the level, and how to report*; *Review build ends the run*; *A skipped step's line carries its evidence and date*; *Records that disagree stop the run*; *The prose holds the fixed lines the tests check*; and *lets-go commits the discovery map on the story's branch*, for one phrase. Scenario headings keep their names. | Evidence: `openspec/specs/lets-go/spec.md` |
| D15 | What do the tests pin? | In `tests/skill-interfaces.bats`: the `review-plan` row names the `lets-review-plan` skill; the `build` row names the `lets-build` skill and not `lets-review-plan`; `lets-go` holds `--for review-plan`, `Done review plan: <date>. <evidence>`, the new review build line and the table's column headings; the old `Done review plan:` line and `with a Code review section` are gone; `lets-review-plan` says `lets-go`'s review plan step. | Assumption |
| D16 | What stays out? | The step strategy, the resolvers and the report format in `lets`; the *Start* sections #185 moved; the plain-language pass of #187, so the rest of the skill keeps its wording; this repository's synced copies and `openspec/config.yaml`; `lets-review-build`'s flow rule. | Evidence: #186 packet, out; #187 packet |
| D17 | How does a fresh review plan session enter `lets-review-plan`? | The skill gains a *Start*, as `lets-review-build` has one. For an OpenSpec change on its branch, it reads the pull request's body. With no **Plan review** section it reviews. With one, *Check an earlier review* decides: a finished review stops the skill, and anything else runs a new round. *Find the author* reads the `Co-Authored-By` trailers of the plan's commits first. When there is none and the session cannot ask, as `lets-go`'s step sessions cannot, it uses its own family and says so in the report. Without this, the step session would ask who wrote the plan on every run. | Evidence: plan review round 1, finding 1; `skills/lets-review-plan/SKILL.md`, *Find the author* |
| D18 | When does the walk read the change state? | At the plan row and again at the build row, with `openspec instructions apply --change <name> --json`, never once up front. A review plan round can add a task to a built change, and the build row must see `ready`, not a stale `all_done`. | Evidence: plan review round 1, finding 2 |
| D19 | What else names the section that goes? | Two anchor links in `lets-go`, in *Import the glossary checkpoint* and *Commit the discovery map*. The spec's *lets-go commits the discovery map on the story's branch*, which is modified for that phrase. The failed-step sentence keeps its pinned words, `carries on from the first unfinished step`. | Evidence: plan review round 1, finding 3 |
