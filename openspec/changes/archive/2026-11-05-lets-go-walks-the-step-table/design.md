## Context

`skills/lets-go/SKILL.md` keeps its steps in three places. *The steps* lists the five names and says review plan runs inside build on `lets-standard`. *Write the prompt* has a table of prompt rows, with two rows for build: one runs `lets-review-plan` before `lets-build`, the other runs `lets-build` alone. *Print the skip lines* has one bullet per step with its `git log` read. Review plan has no report, so that section builds its `Done` line from the pull request's body after build. *Find the first unfinished step* maps the change state to one step and runs every step from there. *Records that disagree* expects a **Code review** section on every archived change, though `lets-review-build` writes one only when the flow's schema is `lets-standard`.

The five step skills exist, and each stops where its step ends: `lets-plan` at `ready`, `lets-review-plan` when the review is finished, `lets-build` at `all_done`, `lets-review-build` after `gh pr ready`. `lets delegate step --for` takes `review-plan` already. `lets-review-plan` holds *Check an earlier review*: four rules that say when a **Plan review** section no longer covers the plan, and a test that says when a review is finished. Its *Find the author* finds the plan's author from a provenance note, from the session, or by asking. A fresh session has none of the three. The `lets-go` spec and `tests/skill-interfaces.bats` pin the skill's lines, commands and rows as text.

This change is the fifth of the six stacked on #177. #187, the last, rewrites `lets-go` in plain language. So this change moves and replaces sections, and does not restyle the rest. The pinned OpenSpec CLI still reads the 0.7.0 copy of the schema, which lists a `review` artifact before `tasks`. Apply depends on `tasks` alone, so the plan reaches `ready` without it, as the earlier layers did.

## Goals / Non-Goals

**Goals:**
- One step table in `lets-go` says, for each step, its skill, when it is done, its record and its skip line. Every other section reads from it.
- Review plan is a step like the others: a prompt, a session, a report, a relay, a `Done` line.
- A `ready` change whose plan no review covers goes to review plan, not build, on any resume.
- A fresh `lets-review-plan` session can start from the change alone.
- The records check is right on both flows.
- The spec and the tests pin the new shape, and the archive merges the delta.

**Non-Goals:**
- Changing `lets delegate step`, the resolvers or the report format.
- Changing the *Start* sections #185 moved, beyond the lines they print.
- Rewriting the rest of `lets-go` for style, which #187 owns.
- Changing how `lets-review-plan` reviews, or how `lets-review-build` decides to review code.
- Touching the schemas, this repository's synced copies or `openspec/config.yaml`.

## Test Seams

- **Primary test seam:** `tests/skill-interfaces.bats`. It reads `skills/lets-go/SKILL.md`, `skills/lets-review-plan/SKILL.md` and `README.md` as text, and checks fixed strings and table rows.
- **Existing seams reused:** `tests/openspec-compat.bats` and the archive rehearsal in a throwaway worktree, which prove the renamed and modified requirements merge; `nix flake check`, which builds both flows with the changed skills.

## Scrutiny Tier & Blast Radius

- **Tier:** medium
- **Blast radius:** `skills/lets-go/SKILL.md`, most of its second half; `skills/lets-review-plan/SKILL.md`, a new *Start*, *Find the author* and two sentences; one paragraph of `README.md`; `openspec/specs/lets-go/spec.md`; `tests/skill-interfaces.bats`. Outside the repository: every project on the `standard` flow. After `lets sync`, `lets-go` runs review plan in a session of its own, and a resumed `ready` change can go to review plan instead of build.

## Decisions

1. **One table, five columns, under *The step table*.** The section replaces *The steps* and the prompt table of *Write the prompt*. Its columns are Step, Skill, Done when, Record and Skip line. Its rows are `shape`, `plan`, `review-plan`, `build` and `review-build`, keyed by the kebab-case identifier, so a test reads a row with `step_row`. The header line is `| Step | Skill | Done when | Record | Skip line |`, pinned by the spec. Done when and Record are short phrases. The commands that read a record sit in a list under the table, one per step, because a code block cannot live in a cell. Review plan's row says `On lets-minimal, with plan` for Done when, and names its `lets-minimal` line beside the dated one. The paragraph that names the steps, the spoken and kebab-case forms, and shape's `<name>` rules stay above the table. Alternative: keep the prompt table and add a second table for done and record. Rejected: the packet asks for one table, and two tables are two places to drift.
2. ***Walk the step table* replaces *Find the first unfinished step*.** The section keeps three reads up front, in order: the tree, the pull request, the archive folder. Then it walks the rows from the top. At each row it reads that row's Done when. Shape: *Confirm the packet* passed. Plan: the change state is `ready` or `all_done`, or the archive folder exists. Review plan: decision 3. Build: the state is `all_done`, or the archive folder exists. Review build: the archive folder exists. The plan row and the build row each run `openspec instructions apply --change <name> --json` when the walk reaches them, and the build row runs it again even when the plan row did. A review plan round can revise the plan and add a task to a built change, and the build row must see `ready`. Any other `state` shows the CLI's `instruction` and stops, as before. A done row prints its skip line. An unfinished row runs as *Run a step* says, and a `done` report prints its `Done` line and moves the walk on. The archive folder still means every row is done, and its checks stay in the reads. Alternative: keep one first unfinished step and run every later step. Rejected: a built change with no plan review would run build again, and review plan's done-ness cannot be read before plan runs. Alternative: read the state once, before the walk. Rejected by the plan review: a `REVISE` round that adds a task would leave build skipped on a stale `all_done`.
3. **Review plan is done when the section covers the plan, by `lets-review-plan`'s rules.** `lets-go` reads the body with `gh pr view <name> --json number,body` when it reaches the row. It finds the `## Plan review` heading, and takes `Reviewed:` and `- **Verdict:**` from inside it. Then it applies *Check an earlier review* of `lets-review-plan`: the four rules that call for a new round, and the test that the review is finished. That test includes the fix commits under `APPROVE_WITH_CHANGES`. Those are `git merge-base --is-ancestor`, `git log <sha>..HEAD` on the plan's paths and `git show` on fix commits, all read-only. The skill names the section instead of copying its rules. So the gate lives in one place, and a later change to the rules reaches both skills. On `lets-minimal`, the row is done with plan and prints its `lets-minimal` line. When the row is not done, the review plan step runs, whatever the `state`. Its session runs the same check through `lets-review-plan`'s new *Start*, decision 9. Alternative: `lets-go` checks only that the section exists with both lines. Rejected: a plan edited after the review would build unreviewed, and the earlier layer's design named that as the reason for the rules.
4. **The review plan step is a step like the others.** Its prompt comes from the frame with `review-plan` as `<step>`, its `--for` is `review-plan`, and its `--name` is `<name>-review-plan`. Its session invokes `lets-review-plan`, whose *Start* reviews or applies *Check an earlier review*, runs its rounds, and writes the section. The frame's evidence rule gains one line: for review plan, the first evidence line is `Plan review: <verdict> for <sha>`, as shape's first line is the issue. The two-`REVISE` stop in `lets-review-plan` is a stop that needs the user. The frame already turns one into a `needs-input` report, so the relay needs no new rule. The `Done` line is `Done review plan: <date>. <evidence>`, from the report, like every other step. The case in *Read the report* and *End of the run* that built a `Done` line from the body goes, and so does the re-read of the body after build. Alternative: keep the constructed line, read from the body after the step. Rejected: the report carries the verdict already, and one line form per outcome is the point.
5. **Every prompt says to invoke the row's skill and stop where it stops.** *Write the prompt* fills *What to run* with one sentence for plan, review plan, build and review build: invoke the `<skill>` skill for the change `<name>`, for issue #<i>, and stop where that skill stops. The step skills own their stops: `lets-plan` at `ready`, `lets-review-plan` when the review is finished, `lets-build` at `all_done`, `lets-review-build` after `gh pr ready`. The frame's second line gains `Route: <route line>.` after the schema. So `lets-plan` has the route line for the proposal commit, and the other steps carry a line they ignore. Shape keeps *What shape runs*, and its two header lines keep no schema and no route. Alternative: keep one bespoke sentence per row. Rejected: the packet says `lets-go` stops carrying a prompt row per step, and each bespoke sentence repeated a stop the skill already states.
6. **Review build is done when the archive folder exists and the pull request is ready, and the code review is the flow's business.** The archive row of *Records that disagree* asks for a **Code review** section only when the `schema:` line of `openspec/config.yaml` is `lets-standard`, which *Route* already reads as the flow's schema. The skip line is `Skipped review build: archived <date> (<sha>); pull request #<p> is ready for review.` on every flow. The row for a built change with no **Plan review** section goes: the walk reaches review plan first and runs it. Alternative: a second line that keeps `with a Code review section` on `lets-standard`. Rejected: two strings for one step, and the section is one `gh pr view` away.
7. **Lines print as the walk goes, and *End of the run* prints the URL.** A row prints its line when the walk settles it: `Skipped` when done before this run, `Done` after a `done` report, `Failed` after a `failed` one. *Read the report* loses the review plan clauses. *End of the run* keeps the example of five lines as the shape of a run's output, says a failed step ends the walk, and prints the pull request's URL. The failed message keeps its pinned words: running `lets-go` again on that branch carries on from the first unfinished step. The spec and the test pin that sentence, and it is still true: the walk's first unfinished row. Alternative: collect the lines and print them at the end. Rejected: a step can take an hour, and the user reads the lines as they come.
8. **What moves in the skill, and what stays.** *The step table* takes the place of *The steps*. *Walk the step table* takes the place of *Find the first unfinished step* and *Print the skip lines*, with the record reads under the table. The two anchor links to the old section, in *Import the glossary checkpoint* and *Commit the discovery map*, point at *Walk the step table*. *Records that disagree*, *Write the prompt*, *Run a step*, *Read the report*, *Relay the questions* and *End of the run* stay where they are. Each is edited where it named the build-row gate or the constructed review plan line. The description and the intro say that every step runs in a fresh session. *Start* changes in one place: step 5's shape line is unchanged, and the text that follows *Start* names the walk. Nothing else is rewritten.
9. **`lets-review-plan` gains a *Start*, and finds the author from the commits.** A fresh session runs the skill from the change alone, so the skill needs a door, as `lets-review-build` has one. *Start*: for an OpenSpec change on its branch, read the pull request's body with `gh pr view --json body`. With no **Plan review** section, run the review. With one, follow *Check an earlier review*. When it says the review is finished and needs no new round, say so and stop. Otherwise run a new round. *Find the author* gains a step before *This session*: read the `Co-Authored-By` trailers of the plan's commits, `git log --format='%(trailers:key=Co-Authored-By,valueonly)' <base>..HEAD -- openspec/changes/<name>/ docs/decisions/ | sort -u`, where `<base>` is the pull request's base from `gh pr view --json baseRefName`. Each family named is an author. When no commit has one, and the session did not write the plan, and it cannot ask, as `lets-go`'s step sessions cannot, it takes its own family as `<family>`. The report says the plan's author was not recorded. The step session usually runs in the same harness and chain as the plan session, so its own family is the best estimate it has. The report records the reviewer and whether the review was independent. The description and *When to apply* say `lets-go`'s review plan step runs the skill before the build step builds a `lets-standard` change. Alternative: `lets-go` passes the plan step's family in the prompt. Rejected: the step record lives in `.workspace/` on one machine, and a resumed run has none. Alternative: stop and ask through a `needs-input` report. Rejected by the plan review: the question would come back on every `lets-standard` run.
10. **The README changes in one paragraph.** Its `lets-go` section says the run has plan, review plan, build and review build, each in a fresh session, and that review plan runs on `lets-standard` only. The glossary's *Step* already lost its exception on this branch. The schemas stay: `lets-standard`'s apply instruction says `lets-go` has the plan reviewed before it, which is still true.
11. **The spec renames two requirements and modifies ten.** *lets-go finds the first unfinished step* becomes *lets-go walks the step table*. *Review plan is reported as not in the route* becomes *Review plan runs as a step, or is not in the route*. The renamed and eight other requirements carry `MODIFIED` blocks with their scenario headings kept, and new scenarios added. *lets-go commits the discovery map on the story's branch* is modified for one phrase, the section it names. The rehearsed archive merged the delta.
12. **The tests pin the table and the rows.** The `lets-standard` and other-schema build-row tests become one: `step_row build` names the `lets-build` skill and not `lets-review-plan`. A new test reads `step_row review-plan` for the `lets-review-plan` skill. The pins gain the table's header line, `--for review-plan`, `Done review plan: <date>. <evidence>`, `Plan review: <verdict> for <sha>` and the new review build line. They lose the constructed `Done review plan:` line and `with a Code review section`. The test that reads `lets-review-plan` for `` `lets-go`'s build step `` reads `` `lets-go`'s review plan step ``, `## Start` and `Co-Authored-By`. The plan-row test that looks for `<route line>` reads the frame instead. The comment over the Plan review test says review plan is a step. A negative pin fails when `lets-go` or the README's `lets-go` section says `runs inside build`.

None of these is costly to reverse. ADR-017 records that `lets-go` reads where a run stands from Git and GitHub. ADR-019 records that the plan review records in the pull request. The walk and the covering check are those two records applied. The ADR step confirms that nothing new qualifies.

## Risks / Trade-offs

- [`lets-go` runs `lets-review-plan`'s staleness rules itself, and the two drift] → The skill names the section by reference and copies no rule. A test pins the reference, and the step session runs the same check in its *Start*.
- [A built change with no plan review now gets one after the fact] → The review covers the plan the build followed. `lets-review-plan`'s tasks exclude keeps ticked tasks out of rule 4. Before, the run stopped and told the user to run the same skill by hand. The build row reads the state again, so a round that adds a task is built.
- [A review plan step session delegates a review from inside a session] → The build step did the same on `lets-standard` since the plan review left the schema. Nothing new is nested.
- [The author's family is a guess when no commit carries a trailer] → The report says so, and names the reviewer and whether the review was independent. A plan commit with a `Co-Authored-By` trailer removes the guess.
- [The route line reaches every prompt, including review build] → One line the skill ignores. The plan step is the only reader.
- [The walk re-reads the pull request body at review plan, and the state at build, on every resume] → One `gh pr view` and one `openspec instructions`, each cheap.
- [`openspec archive` refuses the renamed requirements] → `openspec validate --strict` passes, and the rehearsed archive in a throwaway worktree merged the delta. The last task rehearses it again.
- [The skill's second half changes shape right before #187 rewrites it] → The move is section for section, and #187 reads the result, not the diff.

## Migration & Rollback

No data changes shape. A project upgrades with `lets sync`, which copies the changed `lets-go` and `lets-review-plan`. A `lets-standard` change in flight with a **Plan review** section resumes at build when the section covers the plan, and at review plan otherwise. Rollback is reverting the branch's commits.
