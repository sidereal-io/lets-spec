## Context

`skills/lets-go/SKILL.md` keeps its steps in three places. *The steps* lists the five names and says review plan runs inside build on `lets-standard`. *Write the prompt* has a table of prompt rows, with two rows for build: one that runs `lets-review-plan` before `lets-build`, and one that runs `lets-build` alone. *Print the skip lines* has one bullet per step with its `git log` read, and a long case for review plan, which has no report, so `lets-go` builds its `Done` line from the pull request's body after build. *Find the first unfinished step* maps the change state to one step and runs every step from there. *Records that disagree* expects a **Code review** section on every archived change, though `lets-review-build` writes one only when the flow's schema is `lets-standard`.

The five step skills exist, and each stops where its step ends: `lets-plan` at `ready`, `lets-review-plan` when the review is finished, `lets-build` at `all_done`, `lets-review-build` after `gh pr ready`. `lets delegate step --for` takes `review-plan` already. `lets-review-plan` holds *Check an earlier review*, the four rules that say when a **Plan review** section no longer covers the plan, and says when a review is finished. The `lets-go` spec and `tests/skill-interfaces.bats` pin the skill's lines, commands and rows as text.

This change is the fifth of the six stacked on #177. #187, the last, rewrites `lets-go` in plain language, so this change moves and replaces sections but does not restyle the rest. The pinned OpenSpec CLI still reads the 0.7.0 copy of the schema, which lists a `review` artifact before `tasks`; apply depends on `tasks` alone, so the plan reaches `ready` without it, as the earlier layers did.

## Goals / Non-Goals

**Goals:**
- One step table in `lets-go` says, for each step, its skill, when it is done, its record and its skip line, and every other section reads from it.
- Review plan is a step like the others: a prompt, a session, a report, a relay, a `Done` line.
- A `ready` change whose plan no review covers goes to review plan, not build, on any resume.
- The records check is right on both flows.
- The spec and the tests pin the new shape, and the archive merges the delta.

**Non-Goals:**
- Changing `lets delegate step`, the resolvers or the report format.
- Changing the *Start* sections #185 moved, beyond the lines they print.
- Rewriting the rest of `lets-go` for style, which #187 owns.
- Changing how `lets-review-plan` reviews, or how `lets-review-build` decides to review code.
- Touching the schemas, this repository's synced copies or `openspec/config.yaml`.

## Test Seams

- **Primary test seam:** `tests/skill-interfaces.bats`. It reads `skills/lets-go/SKILL.md`, `skills/lets-review-plan/SKILL.md` and `README.md` as text, and checks fixed strings and table rows.
- **Existing seams reused:** `tests/openspec-compat.bats` and the archive rehearsal in a throwaway worktree, which prove the renamed and modified requirements merge; `nix flake check`, which builds both flows with the changed skills.

## Scrutiny Tier & Blast Radius

- **Tier:** medium
- **Blast radius:** `skills/lets-go/SKILL.md`, most of its second half; two sentences in `skills/lets-review-plan/SKILL.md`; one paragraph of `README.md`; `openspec/specs/lets-go/spec.md`; `tests/skill-interfaces.bats`. Outside the repository: every project on the `standard` flow. After `lets sync`, `lets-go` runs review plan in a session of its own, and a resumed `ready` change can go to review plan instead of build.

## Decisions

1. **One table, five columns, under *The step table*.** The section replaces *The steps* and the prompt table of *Write the prompt*. Its columns are Step, Skill, Done when, Record and Skip line, and its rows are `shape`, `plan`, `review-plan`, `build` and `review-build`, keyed by the kebab-case identifier so a test can read a row with `step_row`. The header line is `| Step | Skill | Done when | Record | Skip line |`, pinned by the spec. Done when and Record are short phrases; the commands that read a record sit in a list under the table, one per step, because a code block cannot live in a cell. Review plan's row says `On lets-minimal, with plan` for Done when and names `lets-minimal` in its skip line beside the dated one. The paragraph that names the steps, the spoken and kebab-case forms, and shape's `<name>` rules stay above the table. Alternative: keep the prompt table and add a second table for done and record. Rejected: the packet asks for one table, and two tables are two places to drift.
2. ***Walk the step table* replaces *Find the first unfinished step*.** The section keeps the four reads in order: the tree, the pull request, the archive folder, the change state. Then it walks the rows from the top. At each row it reads that row's Done when: shape from *Confirm the packet*; plan from a `state` of `ready` or `all_done` or the archive folder; review plan as decision 3 says; build from `all_done` or the archive folder; review build from the archive folder. A done row prints its skip line. An unfinished row runs as *Run a step* says, and a `done` report prints its `Done` line and moves the walk on. The walk reads a row when it reaches it, not up front: a plan step in this run opens the pull request that review plan's row reads, and a review plan step changes the body. The archive folder still means every row is done, and its checks stay in the reads. Alternative: keep one first unfinished step and run every later step. Rejected: a built change with no plan review would run build again, and review plan's done-ness cannot be read before plan runs.
3. **Review plan is done when the section covers the plan, by `lets-review-plan`'s rules.** `lets-go` reads the body with `gh pr view <name> --json number,body` when it reaches the row, finds the `## Plan review` heading, and takes `Reviewed:` and `- **Verdict:**` from inside it. Then it applies *Check an earlier review* of `lets-review-plan`: the four rules that call for a new round, and the test that the review is finished, including the fix commits under `APPROVE_WITH_CHANGES`. Those are `git merge-base --is-ancestor`, `git log <sha>..HEAD` on the plan's paths and `git show` on fix commits, all read-only. The skill names the section instead of copying its rules, so the gate lives in one place and a later change to the rules reaches both skills. On `lets-minimal`, the row is done with plan and prints its `lets-minimal` line. When the row is not done, the review plan step runs, whatever the `state`; the step's `lets-review-plan` runs the same check and decides between a new round and nothing. Alternative: `lets-go` checks only that the section exists with both lines. Rejected: a plan edited after the review would build unreviewed, and the earlier layer's design named that as the reason for the rules.
4. **The review plan step is a step like the others.** Its prompt comes from the frame with `review-plan` as `<step>`, its `--for` is `review-plan`, and its `--name` is `<name>-review-plan`. Its session invokes `lets-review-plan`, which reviews or applies *Check an earlier review*, runs its rounds, and writes the section. The frame's evidence rule gains one line: for review plan, the first evidence line is `Plan review: <verdict> for <sha>`, as shape's first line is the issue. The two-`REVISE` stop in `lets-review-plan` is a stop that needs the user, and the frame already turns one into a `needs-input` report, so the relay needs no new rule. The `Done` line is `Done review plan: <date>. <evidence>`, from the report, like every other step. The case in *Read the report* and *End of the run* that built a `Done` line from the body goes, and so does the re-read of the body after build. Alternative: keep the constructed line, read from the body after the step. Rejected: the report carries the verdict already, and one line form per outcome is the point.
5. **Every prompt says to invoke the row's skill and stop where it stops.** *Write the prompt* fills *What to run* with one sentence for plan, review plan, build and review build: invoke the `<skill>` skill for the change `<name>`, for issue #<i>, and stop where that skill stops. The step skills own their stops: `lets-plan` at `ready`, `lets-review-plan` when the review is finished, `lets-build` at `all_done`, `lets-review-build` after `gh pr ready`. The frame's second line gains `Route: <route line>.` after the schema, so `lets-plan` has the route line for the proposal commit and the other steps carry a line they ignore. Shape keeps *What shape runs*, and its two header lines keep no schema and no route. Alternative: keep one bespoke sentence per row. Rejected: the packet says `lets-go` stops carrying a prompt row per step, and each bespoke sentence repeated a stop the skill already states.
6. **Review build is done when the archive folder exists and the pull request is ready, and the code review is the flow's business.** The archive row of *Records that disagree* asks for a **Code review** section only when the `schema:` line of `openspec/config.yaml` is `lets-standard`, which *Route* already reads as the flow's schema. The skip line is `Skipped review build: archived <date> (<sha>); pull request #<p> is ready for review.` on every flow. The row for a built change with no **Plan review** section goes: the walk reaches review plan first and runs it. Alternative: a second line that keeps `with a Code review section` on `lets-standard`. Rejected: two strings for one step, and the section is one `gh pr view` away.
7. **Lines print as the walk goes, and *End of the run* prints the URL.** A row prints its line when the walk settles it: `Skipped` when done before this run, `Done` after a `done` report, `Failed` after a `failed` one. *Read the report* loses the review plan clauses, and *End of the run* keeps the example of five lines as the shape of a run's output, says a failed step ends the walk, and prints the pull request's URL. The failed message still names the step and the branch, and says `lets-go` on the branch carries on. Alternative: collect the lines and print them at the end. Rejected: a step can take an hour, and the user reads the lines as they come.
8. **What moves in the skill, and what stays.** *The step table* takes the place of *The steps*. *Walk the step table* takes the place of *Find the first unfinished step* and *Print the skip lines*, with the record reads under the table. *Records that disagree*, *Write the prompt*, *Run a step*, *Read the report*, *Relay the questions* and *End of the run* stay where they are, each edited where it named the build-row gate or the constructed review plan line. The description and the intro say that every step runs in a fresh session. *Start* changes in one place: step 5's shape line is unchanged, and the text that follows *Start* names the walk. Nothing else is rewritten.
9. **Two sentences in `lets-review-plan`, one paragraph in the README.** `lets-review-plan`'s description and *When to apply* say `lets-go`'s review plan step runs the skill before the build step builds a `lets-standard` change. The README's `lets-go` section says the run has plan, review plan, build and review build, each in a fresh session, and that review plan runs on `lets-standard` only. The glossary's *Step* already lost its exception on this branch. The schemas stay: `lets-standard`'s apply instruction says `lets-go` has the plan reviewed before it, which is still true.
10. **The spec renames two requirements and modifies nine.** *lets-go finds the first unfinished step* becomes *lets-go walks the step table*; *Review plan is reported as not in the route* becomes *Review plan runs as a step, or is not in the route*. The renamed and seven other requirements carry `MODIFIED` blocks with their scenario headings kept, and new scenarios added. The rehearsed archive merged the delta: two renamed, nine modified.
11. **The tests pin the table and the rows.** The `lets-standard` and other-schema build-row tests become one: `step_row build` names the `lets-build` skill and not `lets-review-plan`. A new test reads `step_row review-plan` for the `lets-review-plan` skill. The pins gain the table's header line, `--for review-plan`, `Done review plan: <date>. <evidence>`, `Plan review: <verdict> for <sha>` and the new review build line, and lose the constructed `Done review plan:` line and `with a Code review section`. The test that reads `lets-review-plan` for `` `lets-go`'s build step `` reads `` `lets-go`'s review plan step ``. The plan-row test that looks for `<route line>` reads the frame instead. The comment over the Plan review test says review plan is a step. A negative pin fails when `lets-go` or the README's `lets-go` section says `runs inside build`.

None of these is costly to reverse. ADR-017 records that `lets-go` reads where a run stands from Git and GitHub, and ADR-019 that the plan review records in the pull request; the walk and the covering check are those two records applied. The ADR step confirms that nothing new qualifies.

## Risks / Trade-offs

- [`lets-go` runs `lets-review-plan`'s staleness rules itself, and the two drift] → The skill names the section by reference and copies no rule. A test pins the reference, and the step session runs the same check before it reviews.
- [A built change with no plan review now gets one after the fact] → The review covers the plan the build followed, and `lets-review-plan`'s tasks exclude keeps ticked tasks out of rule 4. Before, the run stopped and told the user to run the same skill by hand.
- [A review plan step session delegates a review from inside a session] → The build step did the same on `lets-standard` since the plan review left the schema; nothing new is nested.
- [The route line reaches every prompt, including review build] → One line the skill ignores. The plan step is the only reader.
- [The walk re-reads the pull request body at review plan on every resume] → One `gh pr view`, which the earlier design already ran after build.
- [`openspec archive` refuses the renamed requirements] → `openspec validate --strict` passes, and the rehearsed archive in a throwaway worktree merged two renamed and nine modified requirements. The last task rehearses it again.
- [The skill's second half changes shape right before #187 rewrites it] → The move is section for section, and #187 reads the result, not the diff.

## Migration & Rollback

No data changes shape. A project upgrades with `lets sync`, which copies the changed `lets-go` and `lets-review-plan`. A `lets-standard` change in flight with a **Plan review** section resumes at build when the section covers the plan, and at review plan otherwise. Rollback is reverting the branch's commits.
