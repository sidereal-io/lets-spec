## Story

#153 lets-go-from-idea — lets-go takes an idea in words, shapes it into one issue, and carries on with it. https://github.com/sidereal-io/lets-spec/issues/153

The user delegated this brainstorm to the orchestrating session on 2026-11-04 and asked for a recommendation on every question. Each recommendation is recorded as an `Assumption`, so the plan review checks it. The issue has no comments. The packet was last edited on 2026-11-04.

## Decisions

| # | Question | Answer | Source |
|---|---|---|---|
| D1 | What counts as an idea? | A request on the default branch that names no issue. A request names an issue when it holds `#<n>` or is a bare number. A leading or trailing `ask` or `recommend` names the level, as today, and is not part of the idea. Everything else in the request is the idea, kept word for word. | Assumption |
| D2 | Does a change's branch take an idea? | No. On a change's branch the branch names the change. Given words there, `lets-go` says an idea needs the default branch, and stops. | Assumption |
| D3 | Who searches for an existing issue? | Start does, in this session, by naming `lets-build`'s *Find the source of demand* case 2: "The user described work but named no issue." It shows the matches and asks the user, at either level, whether one is the same work. A yes makes that issue `<i>`, and the run goes on as for an issue number. A no, or no match, sends the idea to the shape step. The stop in that case, "say to run `lets-shape`", is set aside, like the blocker stop in #152. | Evidence: `skills/lets-build/SKILL.md`; Assumption |
| D4 | Does the shape step run for an issue that exists but is not shaped? | Yes. Every stop in *Confirm the packet* whose remedy is "run `lets-shape` on #<i>" sends the issue to the shape step instead: not on the Project or no Kind, a missing or placeholder line, or unread comments. The Epic stop stands. `lets-shape`'s single-issue mode already takes "an open issue that has no packet", and the search in D3 often finds one. The shape step runs at most once per run: after it, a *Confirm the packet* stop stands (review finding 3). | Evidence: `skills/lets-shape/SKILL.md` (Shape one issue); #148 Scope; Assumption |
| D5 | How does the shape step run? | As a fourth step, `shape`, through `lets delegate step run --for shape`, with the same prompt frame, relay and subagent fallback as the others. Its row runs `lets-shape`'s *Shape one issue* for the idea, or for #<i>, to its end: the second comment fetch, the reply, and the glossary handoff. The step ends on the default branch with a clean tree. It creates no change and no change branch; a glossary holding branch is `lets-shape`'s own. The packet confirmation is a confirmation question, with no recommendation (review finding 1). | Evidence: ADR-015; #148 Shared decisions; Assumption |
| D6 | What does the shape prompt tell the step about the search? | That Start has searched, and the user confirmed no open issue is the same work, so it skips the search in step 1 and creates the issue. For an existing issue, it names #<i> and says to shape it. | Assumption |
| D7 | Which level does the shape step run at? | The user's `ask` or `recommend` when named. Otherwise `ask`, because the Kind is not settled before shape, and shape is where the work's meaning is captured. Start prints `Interactivity: ask, because shape has not run yet.` After shape, step 10 picks the level again from the packet's Kind, unless the user named one, and prints its line as today. | Evidence: #148 Shared decisions; Assumption |
| D8 | How does `lets-go` learn the issue the shape step wrote? | From the report. The prompt row says the first evidence line of a `done` report is `issue #<n>: <title>`, and `lets-go` reads `<n>` from it. A `done` report whose first evidence line is not in that form is a `failed` report, with the reason that the shape step named no issue. | Assumption |
| D9 | What runs after the shape step reports done? | Start goes on from step 3 with `<i>`, as for an issue number: the blocker read, *Confirm the packet*, *Route*, the branch check and *Claim*. The shape line at step 5 is `Done shape: <date>. <evidence>`, the `Done` form of *End of the run*, instead of the `Skipped` form. | Assumption |
| D10 | What names the shape step's scratch files, with no change name yet? | `<name>` for the shape step is `issue-<i>` for an existing issue, and `idea-<slug>` for an idea. The slug: split the idea on white space, lower-case each word, keep only letters and digits, drop a word left empty, and join the first five words with hyphens, or all of them when there are fewer. The same idea typed again finds its answers file. Once the shape step reports `done` or `failed`, `lets-go` removes that answers file, so a later idea with the same first words, or the same issue shaped again, starts clean (review findings 2 and 5). | Assumption |
| D11 | What happens when the idea is too large for one issue? | `lets-shape` stops at Size L or XL and offers discovery. The prompt row tells the step to end with a `failed` report that says the idea is too large for one issue and names `lets-shape` discovery. `lets-go` prints `Failed shape: <reason>` and stops. There is no branch to name, so the failed line says to run `lets-shape` on the idea. #154 adds the discovery path. | Evidence: `skills/lets-shape/SKILL.md` (step 6); #154 packet; Assumption |
| D12 | Does the prompt frame change? | Only its first lines. For shape, `Issue:` is `#<i>` or `none yet: the idea is <idea>`, `Branch:` is the default branch, and `Schema:` is left out, because *Route* has not run. The `## Questions` and `## The report` sections do not change. The subagent fallback runs shape on the default branch. | Assumption |
| D13 | Do `lets-build` or `lets-shape` change? | No. `lets-go` names `lets-build`'s case 2 and sets its stop aside; `lets-shape`'s single-issue mode runs as it is inside the step, and its glossary handoff questions reach the user through the relay. | Evidence: `skills/lets-build/SKILL.md`; `skills/lets-shape/SKILL.md` |
| D14 | Which routing rows and docs change? | The `lets-go` row in `overlays/AGENTS.md` and the README's usage table becomes `Take a shaped story, bug or chore, or an idea in words, to a ready pull request in one run`. The `lets-shape` rows stay: shaping alone is still a request. The README's `lets-go` section and the skill's description say it takes an idea, and what happens to an unshaped issue. | Evidence: `tests/skill-interfaces.bats`; Assumption |
| D15 | What changes in files? | `skills/lets-go/SKILL.md`: the description, Start step 2 and the new shape path, steps 5 and 10, *Find the first unfinished step* (its "shape is done" and "Start has printed shape's line" sentences), the step list, the prompt frame, *Read the report*, the subagent fallback and *End of the run*. `openspec/specs/lets-go/spec.md`: the modified requirements, one new one for the shape step, and its `## Purpose`, which a delta cannot change. `tests/skill-interfaces.bats`: the new fixed strings and the new row text. `overlays/AGENTS.md` and `README.md`. `flows.json`, `lets-build` and `lets-shape` are unchanged. | Evidence: #153 packet |
| D16 | New glossary terms? | None committed. A candidate, kept tentative: *Idea*, a request to `lets-go` in words with no issue number, which the shape step turns into one issue. The user may settle it; the skill uses "idea" in its everyday sense until then. | Assumption |
| D17 | Can it run here now? | No. The pinned `lets` 0.7.0 has no `step` command. The tests check the skill's prose, as in #149, #150 and #152. | Evidence: `mise.toml` |
