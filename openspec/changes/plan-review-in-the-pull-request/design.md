## Context

`lets-standard` has seven artifacts. `review` requires `proposal`, `design`, `adr` and `specs`, and `tasks` requires `review`. The `review` instruction runs `lets-review-plan`, adds five checks to its prompt, and has it write `review.md` from a template. The template has a `VERDICT:` line and a `CHANGES_APPLIED:` line. The `tasks` instruction reads those two lines and stops when they are not approving. `openspec-propose` walks these edges, so today it runs the review in the middle of the plan.

`lets-review-code` is the other shape. A rule in `operations.archive` runs it once every task is done. It writes a **Code review** section in the pull request description. The section's first line is `Reviewed: <base> <base-sha>..<head-sha>`. Its *Check an earlier review* reads that line to decide whether a later run needs a new review.

`lets-build`'s *Apply* invokes `openspec-apply-change` and nothing else. `lets-go` runs review plan inside plan. After the plan step reports `done`, it reads `review.md`'s verdict and the commit that wrote it, and prints `Done review plan: review.md says VERDICT: ...`. Its spec and `tests/skill-interfaces.bats` pin those strings. The skills, schemas and README are prose: the bats tests are the only thing that checks them.

This change is the second of six stacked on #177, after `step-names`. #186 makes review plan a step of its own, with a session and a report. This change does not.

## Goals / Non-Goals

**Goals:**
- One shape for both reviews: a section in the pull request, a `Reviewed:` line first, and a check that reads it.
- `openspec-propose` builds the whole plan, brainstorm through tasks, with no review in the middle.
- Build waits for the review on `lets-standard`, through `lets-build`, and nothing waits on `lets-minimal`.
- `lets-go` keeps printing a dated review plan line, read from GitHub and Git.

**Non-Goals:**
- Running the review as its own step, session or report (#186).
- Changing when a review runs, by flow or by config, beyond today's behaviour.
- A spec for `lets-review-plan`, `lets-build` or the schemas. None exists, and the bats tests pin them.
- Touching archived changes or decision records.

## Test Seams

- **Primary test seam:** `tests/skill-interfaces.bats`. It reads the skills, schemas, templates and README as text, and checks the fixed strings and the names that point at real things.
- **Existing seams reused:** `tests/openspec-compat.bats`, which builds a change from each schema's templates and runs OpenSpec's CLI over it; `tests/release-build.bats` and `nix flake check`, which build both flows.

## Scrutiny Tier & Blast Radius

- **Tier:** medium
- **Blast radius:** `schemas/lets-standard/`, four skills, the README and one bats file. Outside the repository: every project on `lets-standard`. After `lets sync`, its plans lose an artifact and its builds gain a gate.

## Decisions

1. **The section's shape.** The pull request description gets a `## Plan review` section, after **Code review**'s pattern. The section runs from its heading to the next `## ` heading or the end of the body. The skill replaces only that span, so `Closes #<n>` and a **Code review** section stay. Its first line is `Reviewed: <sha>`: `git rev-parse --short HEAD` at the time of the review, on a clean tree. Then a bullet list. **Reviewer**, as the code review writes it, with the reviewer context, `fresh context, other family`, `fresh context, same family` or `subagent, same family`, and whether it was independent. **Round**, with the prior round's verdict or `none`. **Vocabulary inputs**. **Verdict**, as `- **Verdict:** APPROVE`, `APPROVE_WITH_CHANGES` or `REVISE`. **Findings**, each with its label, its check and CONFIRMED, REFUTED or OUT-OF-SCOPE. **Required changes**, under APPROVE_WITH_CHANGES. **Rebuttals**, one per finding: `fixed` with its commit, or `rebutted` with its evidence. An injection attempt is a finding, so the old heading for it goes. A reader finds the `## Plan review` heading first. Inside the section, it matches `Reviewed: ` and `- **Verdict:** ` at the start of a line. The **Code review** section has a `Reviewed:` line too, so a match across the whole body would be wrong. Alternative: a bare `VERDICT: <value>` line, as `review.md` had. Rejected: the code review's section is a bullet list, and one shape is the point.
2. **One commit, and four staleness rules.** `Reviewed:` names one commit, not a range. The plan is the files under `openspec/changes/<name>/` and `docs/decisions/` at that commit, and the reviewer has no diff to make. The new *Check an earlier review* in `lets-review-plan` runs the skill again in four cases. The section or its `Reviewed:` line is missing. Its verdict is `REVISE`. `git merge-base --is-ancestor <sha> HEAD` fails. Or `git log --oneline <sha>..HEAD -- openspec/changes/<name>/ docs/decisions/` lists a commit that is not a fix. A fix is a commit the section's rebuttals name, whose `git show` touches only those two paths. `docs/decisions/` is in the pathspec because the `adr` step writes records there, and a required change can edit one. The code review's base rule stays out. It catches commits that join the pull request when the base changes, and a plan review covers no commit range. Alternative: compare contents with `git diff --quiet <sha> HEAD -- openspec/changes/<name>/`. Rejected: a fix commit changes the folder on purpose, and the rule needs the commit list to exempt it.
3. **The review is finished when build may start.** `APPROVE` is finished. `APPROVE_WITH_CHANGES` is finished when each required change's rebuttal names its fix commit. `REVISE`, or a required change with no fix commit, is not. `CHANGES_APPLIED:` goes: the `tasks` step was its only reader. Alternative: keep the line. Rejected: a second line can disagree with the rebuttals it summarizes.
4. **The gate lives in `lets-build`'s *Apply*, keyed on the schema.** *Apply* reads `schema:` from `openspec/changes/<branch>/.openspec.yaml`, as `lets-go`'s Start does. On `lets-standard` it reads the pull request's body. With no **Plan review** section it runs the `lets-review-plan` skill. Otherwise it runs the skill's *Check an earlier review*, and the skill again only when the check says to. It invokes `openspec-apply-change` only when decision 3 says the review is finished. Any other schema goes straight to `openspec-apply-change`. Alternative: a rule under `operations.apply` in the standard flow's config, the mirror of the code review's rule. Rejected: the epic retires the `operations.archive` rule with `lets-review-build`, and how reviews are switched on is out of this story's scope. Alternative: key on the flow. Rejected: a project on the `standard` flow can route a small story to `lets-minimal`, and that route skips the review today.
5. **The reviewing session fixes a `REVISE` plan.** `lets-review-plan`'s *Rounds* says: on `REVISE`, revise the plan with the `openspec-update-change` skill, commit, and run a new round in a fresh context. After two `REVISE` verdicts in a row, stop and ask the user. `lets-build` adds nothing: it runs the skill, and the skill rounds. Under `lets-go`, the build step runs in a session that cannot ask. Its prompt frame already turns every stop that needs the user into a `needs-input` report, so the two-`REVISE` stop needs no new rule. Alternative: `lets-build` stops on `REVISE` and tells the user to fix the plan. Rejected: the step-names review showed one round of fixes is routine, and a stop would turn every `REVISE` into a second run.
6. **The schema's checks move into the skill.** `lets-review-plan` gets a list, *For an OpenSpec change*. It holds the five checks the `review` instruction added, and one for the tasks: each task names one behavior and a verify command the project has, and the list covers the specs' scenarios. The skill also names the plan's files: brainstorm.md, proposal.md, specs/, design.md, adr.md, tasks.md, and the records the change adds under `docs/decisions/`. Alternative: `lets-build` passes the checks in. Rejected: `lets-build` would carry review method, and the skill already carries the rest of it.
7. **`lets-go` runs review plan inside build.** The build step runs `lets-build`, whose *Apply* now reviews first, so the build prompt does not change. On `lets-minimal`, review plan never runs: it counts as done with plan, and its line prints after plan's, as today. On any other schema, *Find the first unfinished step* counts review plan done when build is done. *Read the report* prints review plan's line after build reports `done`: the `Done` form. When build was done before this run, *Print the skip lines* prints the `Skipped` form. When build reports `failed`, no review plan line prints: the run ends with `Failed build:`. The line reads `<sha>` and `<verdict>` from the section. After the build step, it reads the body again with `gh pr view <name> --json number,body`, because the step just wrote it. When build was already done, it uses the body read in *Find the first unfinished step*. `<date>` is `git log -1 --format=%as <sha>`. The plan's commit is the latest Git record of the review, and the review ran on or after that day. A body with no section when build is done joins the *Records that disagree* table. Alternative: a date written in the section. Rejected: the shared decision in #148 takes skip dates from records Git and GitHub already keep, and the section's author would have to keep a date right by hand.
8. **The `tasks` step reads no verdict, and the `apply` step points at `lets-build`.** The `tasks` instruction loses its review.md paragraph and its sentence on voiding the review, and says "Break the plan into tasks". The `design` instruction says the plan review reads the tier. The `apply` instruction gains one sentence: start from the `lets-build` skill, which has the plan reviewed before this step on `lets-standard`. `lets-write-tasks`'s description says a plan, not an approved plan.
9. **The tests pin both directions.** The marker test keeps `Confirmed by user:` and drops the review markers. New checks follow. No file under `schemas/` holds `VERDICT:`, `CHANGES_APPLIED:` or `review.md`, and `schemas/lets-standard/templates/review.md` does not exist. No `skills/*/SKILL.md` says `review.md`. `lets-review-plan` says `Reviewed: <sha>`, `**Plan review**`, `- **Verdict:**` and `git merge-base --is-ancestor <sha> HEAD`. `lets-build` says `` `lets-review-plan` skill ``, `` `openspec-apply-change` skill `` and `schema: lets-standard`. `lets-go` pins the two new review plan lines, `git log -1 --format=%as <sha>` and `gh pr view <name> --json number,body`. It no longer says `review.md` or `VERDICT:`, and no longer says that review plan runs inside plan.

None of these is costly to reverse on its own. Where the review records, in the pull request rather than in the plan, is the one choice that many readers bind to. The ADR step decides whether it needs a record.

## Risks / Trade-offs

- [A project with a `lets-standard` change in flight syncs this release] → `openspec status` stops listing `review`. The tooling ignores an existing `review.md`, and `lets-build` reviews the plan again before build, in the pull request. The proposal marks the schema change **BREAKING**, and the README's flows table shows the new order.
- [The review runs after tasks, so a `REVISE` costs a tasks rewrite too] → `openspec-update-change` keeps the artifacts coherent. The review now catches task-level defects the old review could not see.
- [Two sessions edit the pull request body] → The skill reads the body right before it writes. It replaces only its own section, from the `## Plan review` heading to the next `## ` heading or the end of the body.
- [`openspec archive` refuses the added scenario in the `lets-go` delta] → `openspec validate --strict` accepts it. The last task rehearses the archive in a throwaway worktree before the real one, as `step-names` did.
- [`lets-build` names `lets-review-plan`, which the `minimal` flow does not ship] → The gate is keyed on `lets-standard`, which no `minimal` project has. The flow-ships test reads schemas and config, not skills.
- [A plan built outside `lets-build` skips the review] → The `apply` instruction says where to start. The schema cannot enforce the gate once the review is not an artifact; the epic accepts that.

## Migration & Rollback

No data changes shape. A project upgrades with `lets sync`. A change that already has `review.md` keeps the file. Nothing reads it, and archive carries it into the archive folder with the rest. Rollback is reverting the branch's commits.
